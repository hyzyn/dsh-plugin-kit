## 2. 三条数据通路（**本方案最关键的一节**）

「经目标主机代理为主」这个前提决定了：DSH 宿主**不直接**连数据库，而是先到目标主机。但到了目标主机
之后有两条不同的路，**适用范围完全不同**——选错会让整个实现依赖「目标主机上恰好装了什么客户端」。

### 2.1 通路 A：SSH 通道直通（`forwardOut`）+ 本地驱动

宿主经 ssh2 的 `forwardOut` 开一条到「目标主机视角下的 `host:port`」的通道，把
**数据库线协议直接跑在这条流上**。

**判据是「Node 里有没有该协议的驱动」**：

| 引擎 | 协议 | 能否走通路 A |
|---|---|---|
| MySQL / MariaDB | 公开，`mysql2` | ✅ |
| PostgreSQL | 公开，`pg` | ✅ |
| Redis | 公开（RESP），`ioredis` / 自写 | ✅ |
| **SQL Server** | TDS | ✅ **`tedious`**（2026-10-02 更正：此处原写「❌ 无可用的纯 JS 驱动」——**那句是错的**。实测 `tedious@20.0.0` 是纯 JS，10 个依赖无一原生模块。⚠️ 代价：它带进 `@azure/identity` / `@azure/core-auth` / `@azure/keyvault-keys` 三个 AAD 相关依赖，对「零依赖」的口味是取舍） |
| **RocketMQ** | **私有 + 依赖 `mqadmin` 运维口径** | ❌ |

**收益**：通路 A **完全不要求目标主机装任何客户端**。这对「开发测试方便」是决定性的——否则每个
目标都得先确认有 `mysql` / `redis-cli`，配置面立刻变成一支运维队伍。

### 2.2 通路 B：在目标主机上执行 CLI

经 `RemoteExec.run(spec, argv)` 执行目标主机上的客户端，解析其输出。

**只在通路 A 不可用时用**：

| 引擎 | 用什么 | 前提 |
|---|---|---|
| SQL Server | `docker exec <容器> sqlcmd`（容器自带）或主机上的 `sqlcmd` | 需要 docker 通道 **或** 主机已装 sqlcmd。⚠️ **2026-10-02 实测这条对 cdqas 不成立**：容器里没有 `sqlcmd`，而**库在网络上独立可达**（`192.0.2.247:1433`）→ SQL Server 改走**通路 A**，见 [§17.4.1](#1741-通路-ab-的实测答案sql-server-该走通路-a通路-b-在这台容器上不成立2026-10-02) |
| RocketMQ | `mqadmin`（RocketMQ 自带，通常在 broker/nameserver 容器里） | 同上的通道问题 |

**代价要说清**：通路 B 的成功依赖**目标主机（或容器）里的工具**，而这需要真机确认（见 §4）。
且输出解析是脆的（版本差异、本地化输出）——**每一类解析都要有 fixture 用例**。

### 2.3 结论：通路按「**环境 × 引擎**」分配，不是按引擎

同一个引擎在不同环境里可能走**不同**通路——判据是两条**实测**，不是偏好：

1. **那个端口对 DSH 宿主可达吗**（可达 → 通路 A 可行）；
2. **这个库 / 中间件自己是不是容器化的**（是 → 官方镜像通常自带客户端 → 通路 B 可行）。

**A 优先**（不要求目标侧装客户端、也不用解析脆弱的 CLI 输出）；**两条都不可行 = 这个环境验不了**。

| 环境 | 引擎 | ① 宿主可达 | ② 容器内客户端 | 分配 |
|---|---|---|---|---|
| `192.0.2.247`（Windows 主机） | SQL Server | ✅ `1433` | ❌ 没有容器，`248` 主机上也没有 | **A**（可选驱动 `tedious`，见 §2.4） |
| `192.0.2.161` | MySQL | ❌ `3306` **被丢弃** | ✅ `/usr/bin/mysql`（8.0.39） | **B** |
| `192.0.2.161` | Redis | ❌ `6379` **被丢弃** | ✅ `/usr/local/bin/redis-cli`（6.2.18） | **B** |
| `192.0.2.161` | RocketMQ | 未测（同 161 只放 22） | ✅ `/home/rocketmq/rocketmq-5.3.2/bin/mqadmin` | **B** |
| `192.0.2.248` | Redis / Kafka / Nacos | ✅ `6379`… | —（容器化，但宿主可达） | **A**（优先）——**✅ Redis 已于 2026-10-02 实现并真机验证**（见 §17.4.2）。⚠️ 该 Redis **无密码**（`requirepass` 空）且 **4.0.14 无 ACL** → 只读账号这层不存在，见 §8 |

**两句要看清楚的话**：

- **`161` 的防火墙只放 22**：实测 `8344` / `3306` / `6379` **全被丢弃**（`curl` 超时，不是拒绝）
  → **`161` 上的一切都必须经 SSH / 容器**；而 `247` / `248` 的端口是可达的 → 走 A。
- ⚠️ **`248:3306` 也开着，但 `248` 上没有 mysql 容器**——那**很可能是群晖 DSM 自带的 MariaDB**，
  与项目库无关。**别把它当成项目 MySQL**（待确认）。

### 2.4 引擎驱动一律**可选**（2026-10-02 定，**推翻**上面那句）

上一版在这里写的是「通路 A 需要 `mysql2` / `pg` / `redis` 作为**真实运行时依赖**」——**改掉**：
**驱动由要用的人自己装，`devdata` 的 `dependencies` 里一个驱动都没有。**

**依据是一次实测**：为 SQL Server 引 `tedious` 会带进 **131 个包 / 65 MB**，其中
**42 MB（约 65%）是 `@azure/*`**（Azure AD 认证）——走 SQL 账号认证时**一行都用不到**。
让所有装这套件的人都背上它、只为少数人要验 SQL Server，代价与收益不成比例。
（`tedious` 没有任何版本能避开：`9`/`11` 带 `@azure/ms-rest-nodeauth`，`15`/`16`/`20` 带
`@azure/identity` + `@azure/keyvault-keys`。）

**三条规矩（守卫按这三条判）**：

1. 任何包的 `dependencies` / **`optionalDependencies`** 里都不得出现引擎驱动
   —— `optionalDependencies` 也不行：**npm 默认会装它**，「可选」名存实亡；
2. `devdata` 的 `dependencies` 是**允许清单**（`@hyzyn/dsh-kit` + `js-yaml` + `@deepseek-ai/schemastery`
   ——最后一个是接宿主时加的配置 schema 库，本仓每个带配置的插件都在用它，**不是引擎驱动**）：
   加任何一项都要改守卫，也就是一次**刻意动作**，不是顺手；
3. `src/` 里不得对驱动做**静态** `import`（它会把「缺驱动」变成**加载期崩溃**，并诱导人写进
   `dependencies`）；**`import type` 与 `await import()` 允许**——类型可以待在 `devDependencies`，
   动态 import 才是可选依赖的正确用法。

**缺驱动时的失败要说人话**：`loadOptionalDriver()`（`src/engine-driver.ts`）把
`Cannot find module 'mysql2'` 换成「验 mysql 需要驱动 `mysql2`，**本包刻意不预装**（原因…），
恢复路径：`npm install mysql2`」。**且只换「模块找不到」这一类**——驱动自己加载时抛的错
**原样穿出去**：把真错误说成「没装」，会让人去重装一个本来就装好的包。

**守卫与机制**：`packages/devdata/test/engine-deps.guard.test.ts`（跨包三条判据 + 三条反例）、
`packages/devdata/test/engine-driver.test.ts`（缺驱动 / 真错误两条路径）。

## 3. 能力模型（三档，挂**操作**不挂连接）

### 3.1 不变量（任何实现不得破坏）

1. **能力档判定在「操作」上，不在「连接」上。** 同一份目标凭证不得因为「这条连接是只读档配的」而
   获得超出该档的操作能力——即：**每次调用都要独立判定「操作 × 目标 × 可逆性」**。
   违反的症状是最坏的那种：外层闸门看着很严，实际从旁边那条连接绕过去了。
2. **没有环境标签的目标，不做写操作。** 标签缺失 / 标为生产 → 写类操作一律拒绝，读类照常。
   （理由：本套件自我定位为开发测试，而环境里**没有硬边界**——`248` 同时是测试主机与生产 job 的
   证据来源、`161` 是公网 IP、Jenkins 侧 job 描述里**不含环境属性**。）
3. **凭证不进 DSH 配置文件明文、不进 LLM 上下文。** 走 `resolveSecret` 的 `env:NAME` 路径；日志与
   错误文案里只回显**是否已设置**（照 `docker` 的 `passwordSet` 布尔口径）。
4. **失败不拒绝服务。** 任一引擎连不上，面板其余部分照常可用。

### 3.2 三档

| 档 | 引擎 | 护栏**来自哪** | 默认 |
|---|---|---|---|
| **SQL 只读** | SQL Server / MySQL / PostgreSQL | **库账号强制**（只读账号）+ 代码层 SQL 判定 | 只读 |
| **NoSQL 受限** | Redis | **只有代码层**（没有只读账号这回事）→ 操作白名单 + 范围限制 | 只读命令 |
| **中间件** | RocketMQ | **宿主侧能力授权**（复用 `capabilityGranted`） | 观察面开、操作面关 |

### 3.3 SQL 档：三层护栏，第一层是唯一硬的一层

1. **库账号只读**（硬）：连上去先做一次**只读自证**——尝试一次注定失败的最小写操作，确认它被库拒绝。
   失败则**拒绝启用这一档**（而不是警告后继续）。这是唯一「代码写错也翻不了车」的保障。
2. **语句判定**（软）：只放行 `SELECT` / `SHOW` / `DESCRIBE` / `EXPLAIN` / `information_schema` 查询；
   **拒绝多语句**（分号拼接是典型绕过）。
3. **结果面**（软）：行数硬上限 + 超限截断并**明示截断**（照本仓既有的截断信号口径）。

> **只读账号哪儿来**：`cdqas-sqlserver`（8109→8300）那类容器里可能已有现成账号，也可能需要运维
> 建一个。这是 §4 要真机确认的第一件事——**它决定 SQL 档是「可做」还是「得先要账号」**。

### 3.4 Redis 档：这一档的护栏**没有兜底**，按不可逆对待

Redis 没有只读账号。所以「受限」只能靠代码白名单，而**没有第二层网**。设计上必须体现这一点：

| 类别 | 命令 | 处理 |
|---|---|---|
| 只读 | `GET` `MGET` `TYPE` `TTL` `HGETALL` `LRANGE` `SMEMBERS` `ZRANGE` `SCAN` `INFO` | 默认放行 |
| **危险读** | `KEYS`（阻塞）、`MONITOR`（抓全量流量、含他人数据） | **默认拒**，单独授权 |
| 受限写 | `SET` `DEL` `EXPIRE` `HSET` `LPUSH` … | 需授权；**要能说清「改的哪个 key」** |
| **不可逆 / 影响他人** | `FLUSHDB` `FLUSHALL` `CONFIG SET` `SCRIPT` `EVAL` | **不做**（明确出范围，不给开关） |

`SCAN` 必须带 `COUNT` 上限；`EVAL` / `SCRIPT` 一律不做——它等于把代码执行权交出去，
「操作白名单」在那条命令面前是装饰。

### 3.5 RocketMQ 档：观察与操作**必须两个能力**

| 面 | 内容 | 闸门 |
|---|---|---|
| **观察** | topic 列表 / 消费组 / **堆积量与 lag** / 死信统计 / 消息轨迹（按 key 或 msgId 查） | 默认开（只读） |
| **操作** | 发送消息 / 重置消费位点 / 创建·删除 topic | 独立能力，默认关；**且每个动作二次确认** |

理由：共享测试环境里，一个不可逆动作打到的不是你，是同事的联调。观察面能开到默认，操作面不能。

工具面以 `mqadmin` 为准（通路 B）。**每一类输出解析都要有 fixture**（版本差异 + 中英文输出）。

### 3.6 agent 失败模式（本方案的**主要**消费者是 agent，不是人）

本套件的消费者是 DSH 里的 coding agent；面板是次要的检查面。所以护栏要按 **agent 怎么失败**设计，
不是按「怎么防恶意用户」设计。四类失败模式与对应机制：

| agent 的失败 | 机制 | 依据 |
|---|---|---|
| **写错 / 幻觉出写操作** | AST 级语句分类：**不认识的一律拒**（不是关键字黑名单） | [nyetdb](https://github.com/stasmarkin/nyetdb) 的做法：`nyet query prod "DELETE FROM users"` → `NYET / WRITE_OPERATION` + 一条**改写提示** |
| **无翻页的全表查询**（最贵的一类） | **查询计划护栏**：先取 plan / 估算，超阈值**拒跑**，并把 plan 附在错误里让 agent 一轮修好 | 同上「no `--force`」 |
| **自己放宽限制 / 循环重试** | **上限不可提**：候选只能请求更小，不能更大；策略值**不接受变量插值** | 同上「ceilings the agent cannot raise」 |
| **重复执行 / 留下垃圾数据** | 操作契约里带**幂等性**声明 | 见 §3.7 |

### 3.6.1 工具面清单（**发现 → 理解 → 查询**，缺一节 agent 就走不通）

> **为什么单列一节**：agent 与人流程不同——人先想好「我要看订单表」，agent **先不知道有什么**。
> 只给一个「跑 SQL」的口子，agent 只能靠 `information_schema` 自己拼查询，每一步都在烧 token 且
> 容易猜错；而你这套环境的库表命名是业务缩写（`cdqas` / `bpaoss-njnt`），**猜不中**。
> 参照物：本仓既有的 agent 工具面（`docker_attention` → `docker_ps` → `docker_logs` → …）
> 与 `jenkins-release` 技能的 `getJobs` → `getBuildLog` → `docker_inspect` 是同一模式——
> **工具清单本身就是那套流程的价值**。

> **名字有两种，别混**（2026-10-02 补）：下表用的是**动作名**（矩阵的词汇）；agent 看到与调用的
> **工具名**一律带 `devdata_` 域前缀（`devdata_list_targets` / `devdata_redis_command` …）——
> 仓库守卫要求 `<域>_<动作>`，理由与「工具名是模型选工具时唯一看到的标识」见 §17.14 ①。

**四组，按 agent 的实际推进顺序：**

| 组 | 工具 | 作用 | 缺了会怎样 |
|---|---|---|---|
| **发现** | `list_targets` | 当前目录能用哪些连接（与 §3.7-2 的 `scopeDirs` 同源） | agent 不知道该连哪个，只能乱试 |
| | `search` | **按列名 / 表名搜**（「哪张表有 `order_no`」） | 业务缩写命名猜不中 → 又退化成自己拼 `information_schema` |
| **理解** | `schema` | 表 / 列 / 主键 / 索引 / 外键（可按表过滤） | 不知道列名 → 反复失败重试 |
| | `describe <table>` | 单表结构 + 枚举值（粒度更细、更省 token） | 同上，且更贵 |
| | `sample <table>` | 随机几行（脱敏 + 上限） | **schema 会说谎**：空值率、编码格式、枚举实际值只有样本能说明 |
| **查询** | `query` | 只读语句（§3.6 全套护栏） | 主干 |
| | `explain` | 计划 + 成本，不执行 | 被 plan 护栏拒后，agent 得从中自己解析 plan；单列成一个工具更省一轮 |
| **自证 / 恢复** | `doctor` | 逐层报告只读在哪几层真的在位（§3.7-3） | agent 无法自查「为什么我查不了」 |
| | `capabilities` | 本目标当前档位 + 哪些能力**未授权** + **怎么授权** | 撞闸门后只会反复重试，看不到出路 |

**两条实现要求**：

1. **`capabilities` 的授权文案必须照 kit 的 `capabilityHowTo` 口径**——明确说「在**启动 dsh 的那个
   环境**里 export 后重启」，**不能**说「去设置里点开关」（那样点不动，是本仓已修过的缺陷类型）。
2. **被拒的错误必须带恢复提示**（照 nyetdb 那句 "rewrite the task as a read query" 的写法）。
   agent 的失败模式是**循环重试**，而一句「未授权」不产生新信息，它只能原样再试一次。

**按引擎的差异（不是同一套工具换名字）**：

| 引擎 | 发现类工具落在什么上 |
|---|---|
| SQL Server / MySQL / PostgreSQL | `schema` / `describe` / `search` 走 `information_schema`；`sample` 需受 §3.6 行数上限约束 |
| Redis | 没有 schema 概念：`search` 落在 **`SCAN` + 模式 + `COUNT` 上限**（**不是 `KEYS`**）；`describe` 落在 `TYPE` + `TTL` + 编码；`sample` 落在「若干个 key 的取值」 |
| RocketMQ | `list` 落在 topic / 消费组 / broker 列表；`search` 落在「按 key 或 msgId 查消息轨迹」；`sample` 落在「某 topic 的最近 N 条」。**注意**：按 msgId 查是否**真快**取决于索引配置，属于 §4 要实测的一项 |

### 3.7 三条新增落地要求

1. **凭证来源要标「保护强度」，不能假装等价。** 本仓现有的 `resolveSecret` 只解决「不落明文」，
   但 **agent 与用户同 uid → 环境变量 / 文件 / `op read` 它都能读**。所以要显式区分：
   只给 agent 用**它读不到**的来源（如 macOS Keychain），其余来源在快照 / `doctor` 输出里标成
   「方便，不防护」。**不能把两者都写成「已配置」**——那是对外宣称了一个不成立的性质。
   > 这条直接修正 §1 里「凭证走 `resolveSecret` 就够了」的说法。
2. **作用域按目录收敛，缺省拒绝。** 每个连接声明**从哪些目录可达**（子目录包含在内）；
   缺省或为空 = 处处拒绝（fail-closed）。这同时是并行 agent 的隔离手段（见 §3.8）。
3. **只读必须能**自证**，且失败即拒绝。** 提供一个 `doctor` 类入口，逐层报告哪一层真的在位
   （AST 判定 / 会话级只读 / 只读账号 / 非超级用户 / 配置文件权限），**验不到的一律报 warn、不报 ok**。
   这是 §3.3「只读自证」的展开形式，也让它成为可验收条目而不是口号。

### 3.8 并行 agent 的隔离（**当前方案最大的缺口**）

§5 的 `env` 标签是**二值**的（可用 / 不可写），这假设「一次只有一个 agent 在动这个测试库」。
但并行 agent 是现在的常态：多个 worktree 各跑一个 agent 时，**git worktree 只隔离了代码、没隔离数据**
——三个 agent 对同一个库跑迁移 / 重置种子数据会互相破坏，不管代码分支多干净
（[Database Branching](https://raw.githubusercontent.com/coleam00/cole-medin-knowledge-base/refs/heads/main/concepts/database-branching.md)）。

**所以 `env` 要三态，并且 `test` 要再分两层**：

| 标签 | 含义 | 允许 |
|---|---|---|
| `dev` | 开发者本机的可丢弃实例 | 读写 |
| `test-shared` | 团队共享的联调环境（`248` / `161` 的现状） | 读**全部**；写**受限**（只能幂等操作 + 二次确认） |
| `test-isolated` | 可丢弃的按 worktree / 按任务副本 | 读写；**agent 可自由重置** |
| `unknown` / 缺省 | 未标注 | **只读**（§3.1 不变量 2） |

**`test-isolated` 是这个方案里价值最高、现在完全缺失的一块**：它才是让 agent 能「跑迁移、清表、
灌种子数据、跑完就扔」的前提。没有它，agent 只能读共享环境，或者冒着破坏同事联调的风险去写。

> 实现上不必然是 Neon 那种 copy-on-write（你这套是自建容器）。可行形态：按 worktree 起一份
> 可丢弃的容器化实例、或按任务创建带前缀的库 / schema，用完删除。**这属于 P0 调研要加问的一项。**

### 3.9 验活断言库（**让本套件接上「发布后核对」的那一环**）

§0 说的存在理由之一是「核对发布后的业务数据」。**这一环不能靠人每次现编 SQL**——那样它不可积累、
不可复审、也不能被 agent 自动执行。落法是把验活**断言化**：

```
VerifyAssertion {
  id: string
  project: string                    // 'cdqas' | 'ems' | 'cdc' | 'hcckc' | 'tcml' | 'bpa' | 'jasper'
  appliesTo: 'backend' | 'front' | 'build-only'   // §2 的部署机制：决定「该验什么」
  target: string                     // DevDataTarget.id
  statement: string                  // 只读语句（或受限档操作）
  expect: { eq?: unknown; regex?: string; gte?: number; lte?: number; rowCount?: number }
  severity: 'fail' | 'warn'
  timeoutMs?: number
  note?: string                      // 出现的已知噪声（照 jenkins-release 技能 §4 的口径）
}
```

**四条设计约束**：

1. **断言只读，且复用 §3.6 的全套护栏**（AST 分类 / plan 护栏 / 上限不可提 / 审计）。
   断言库**不新增任何写能力**——它是 §3.2 的消费者，不是第四个能力档。
2. **存成项目内的文本清单**（形态建议 `verify/<project>.yaml`，随项目仓库走版本管理），
   DSH 侧**只读**。理由：断言是**项目知识**，该跟项目一起评审、一起演进，不该藏在一个工具插件里。
   若某项目没有这个文件，则本项目**无断言**（不是「用默认断言」）——缺省即无，fail-closed。
3. **跑批要一次拿全，不是 N 轮对话**：一次调用执行该项目全部断言，返回
   `{ project, ranAt, results:[{id, ok, got, expected, severity, latencyMs}] }`，
   差异用**结构化**形式给出（got / expected 并排），让 agent 一轮就能定位。
4. **与 Jenkins 的关联是「映射」不是「改动」**：`project → job` 的关系照 jenkins-release 技能
   现有的映射表（那份表本来就是从上次成功构建日志现算出来的），**不要求 Jenkins 侧做任何改动**。
   断言跑在**一次发布之后**，结果是「业务是否真的对」，与容器 `StartedAt` / 启动完成行、
   CIFS 传输量**并列**为验活证据。

**这一条的收益**：把「进程起来了」（skill 第 3.1 节现在能做到的）推进到「业务逻辑对了」，
而且**断言本身跨版本累积**——发布越多，验活越自动。这是本方案里唯一直接降低「发布后风险」的
那一项，也是 §0 存在理由 ① 的落地形态。

> **边界**：断言库**不去改动 Jenkins**、不注册新 job、不参与发布本身；它只在发布**之后**跑。

### 4.1 要账号时**要一起要**什么（C2 的执行版，可直接交给运维）

**结论先说：只给 `SELECT` 的账号会让这套工具一条查询都跑不成**——报出来的是我们自己设计的
`PLAN_UNAVAILABLE`（「拿不到计划就拒绝执行」，`plan-guard.ts:186`），**看起来像工具的 bug，
实际是权限没要全**。原因是本套件的 SQL 面**先取计划、再决定跑不跑**（不知道代价就放行等于没有护栏），
所以「能取计划」是和 `SELECT` **同级**的必要权限，不是加分项。

| 引擎 | 要什么 | 为什么 / 注意 |
|---|---|---|
| **SQL Server**（`192.0.2.247:1433`） | `SELECT`（只给它要验的库/模式）**＋ 数据库级 `SHOWPLAN`** | **`SELECT` 单独不够**：取**预估**执行计划要 `SET SHOWPLAN_XML ON`，那需要 `SHOWPLAN` 权限。**不要**用 `SET STATISTICS XML ON` 代替——那个会**真的执行**查询，而我们正是要在执行**前**判断代价 |
| **MySQL**（`161`） | `SELECT` | `EXPLAIN` 只要表上的 `SELECT`，不需要额外权限 |
| **PostgreSQL** | `SELECT` | `EXPLAIN` 同理（**不要** `EXPLAIN ANALYZE`——那个会执行） |
| **达梦 DM** | `SELECT` + **能 `EXPLAIN`**（具体权限项**待确认**） | 别照抄 MySQL 那条：达梦的 `EXPLAIN` 权限我没查到权威说法，**要当场试**（试的办法：用给的账号跑 `EXPLAIN SELECT 1`） |
| **Redis** | ⚠️ **在 `248` 那台上不可能**：Redis 4.0.14 **没有 ACL**、`requirepass` 为空 → **没有「只读账号」这层可要**。要么**接受「代码层是唯一护栏」**，要么换一台 ≥6 的实例、或在前面加一层只读代理 | Redis 不过计划护栏（`guardPlanFor` 只覆盖四个 SQL 引擎）。这一条要**当决策处理**，不是当待办——见 §8 的「Redis 档无兜底」 |

**一并要的还有三件**（都不是权限，但缺了同样做不成）：

1. **连接信息**：库的 host:port（SQL Server 我已实测是 `192.0.2.247:1433`；MySQL / Redis 在
   `161` 上，端口要从容器映射里取——**C3 那一半还没查**）；
2. **明确「这是测试/联调环境的账号」**——本套件的环境四态里，`prod` 档的读也要二次确认，
   而我们**不该**拿生产账号来验；
3. **副本的可能性**（C6）：能不能按任务起一份可丢弃的库副本。**它决定 agent 能不能写**——
   没有它，agent 只能读共享环境。

### 4.2 第一轮的请求：达梦上 `HCKC_EXAM` 的只读账号（2026-10-02）

等于没有护栏）。所以「能取计划」与 `SELECT` 是**同级**的必要权限；少了它，工具会报我们自己的
`PLAN_UNAVAILABLE`，**看起来像工具的 bug，实际是权限没给全**。

**已经确定的事实**（库名由维护者告知；实例与端口是 2026-10-02 实测/核对的）：

## 5. 数据模型

```
DevDataTarget {                      // 一个可访问的数据服务
  id: string                         // 稳定 id
  label: string                      // 显示名
  kind: 'sql' | 'nosql' | 'mq'
  engine: 'sqlserver' | 'mysql' | 'postgres' | 'redis' | 'rocketmq'
  transport: SshSpec | 'direct'      // §2：经目标主机（复用 tty 连接簿）或直连
  endpoint: { host: string; port: number }   // 目标主机视角下的地址
  env: 'dev' | 'test-shared' | 'test-isolated' | 'unknown'   // §3.8：默认 unknown，不是 test
  scopeDirs: string[]                // §3.7-2：从哪些目录可达；空 = 处处拒绝
  capabilities: { read: true; write?: CapabilitySpec; admin?: CapabilitySpec }
  credentialRef?: string             // 'env:NAME' —— 只存引用，永不存明文
  ceilings: { maxRows: number; maxTimeoutMs: number }        // §3.6：**候选只能请求更小**
  isolation?: { kind: 'container' | 'schema' | 'prefix'; reset: CapabilitySpec }  // §3.8
}
```

**四条约束**：
- `env` 是**必填**，没标就是 `unknown`（不是默认 `test`）；
- `credentialRef` 不得是明文；对外只回 `passwordSet: boolean` **与来源的保护强度**（§3.7-1）；
- `ceilings` 是策略值，**不接受变量插值**，也不受候选参数影响（§3.6）；
- `scopeDirs` 为空 = 处处拒绝（fail-closed，§3.7-2）。

**审计面（`test-shared` 及以上写操作必开）**：一条 JSON 行 / 调用，**含被拒绝的尝试与超时**
——它记的是 agent **试过什么**，不只是成功过什么。写不进去就不返回结果（fail-closed）。

## 7. 包与发布策略（**私有包**，需要先处理聚合）

**定位是自用开发测试工具 → `"private": true`。** 但注意本仓两条机制：

1. `scripts/check-publishable.mjs:42` 对 `private === true` 的包**直接跳过**（发布清单不必补行）；
2. **`scripts/aggregate.mjs` 不看 `private`**（已 grep 确认零命中）——它按「`packages/*` 下任何带
   `dsh.bundle.patch` 的包」扫描。所以**只加 `private: true` 并不能阻止它被塞进 `@hyzyn/dsh-all`**。

三条可选处理，**择一，且按 §8 风险项先确认**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **N1（推荐）** | 让 `aggregate.mjs` 跳过 `private === true` 的包 | 动一个脚本 + 同步 `check-publishable` 判据 + 守卫用例；**属 L0，要动 CI/脚本**。**2026-10-01 已落地**（`isAggregatable`）；2026-10-02 实测：本包带上 `dsh.bundle.patch` 之后 `packages/all` 与仓根 bundle 里**依然没有** `devdata` |
| N2 | 包放在 `packages/*` 之外（如 `templates/` 那样不在 workspace 内） | 立刻失去 workspace 依赖与 `tsconfig` 继承；不建议 |
| N3 | 接受它进聚合包但不发 npm | 自相矛盾：聚合包本身会发，装了全家桶的人会拿到一个残缺的聚合 |

> **2026-10-02 补**：本包现在**有** `dsh.bundle.patch`（`cordis.patch.yml`）——它必须能被
> `dsh plugin add link:` 装进 profile，否则「接成宿主插件」这件事根本不成立。N1 落地之后这两件事
> 不再冲突。此前各处（包内 `index.ts` 头注释、README、ROADMAP 记-4）都写着「刻意不带补丁层，
> 因为 aggregate 不看 private」——那条**理由**随 N1 失效，结论也跟着失效，已一并更正。

**公开与否**：仓库已公开 → 源码必然可见，`private: true` 挡的是「别人装得到」，**挡不住「别人看得到」**。
若顾虑的是后者，那是「另开私有仓库」的正当理由，而不是本方案内的选项。

## 13. 环境编排（2026-10-01 追加）

**缺口的证据不在别处，就在本仓自己的 skill 里**：`~/.dsh/skills/jenkins-release/SKILL.md` 花了整节
写「`248` 上 `bpa*`、`svims` 系列容器**多数处于 exited 状态**（exit=143），发布前先确认那些服务
当前是否本该运行」，以及「Spring Boot 热启动 **10~15 秒**，冷启动可达 **150 秒**，构建刚 SUCCESS 时
可能还在启动，需等待或轮询」——**这些全是环境编排的知识，散落在一份人工流程里。**

Docker 面板能看**单个**容器，但回答不了：「把 ems 这一套起起来、等全部就绪、跑完测试、再拆掉」。

### 13.1 工具面

| 工具 | 作用 |
|---|---|
| `env_up <profile>` | 按清单拉起一组服务（compose 项目 / 一组容器） |
| `env_wait <profile>` | 等全部就绪，**按声明式判据**，带超时与逐服务进度 |
| `env_status <profile>` | 每个服务：容器状态 + 就绪判据是否满足 + 已等多久 |
| `env_down <profile>` | 拆除（**保守**：默认只停，不删卷） |

### 13.2 关键设计：就绪判据是**声明式清单**，不是启发式

`env_wait` 最难的不是等待，是**知道在等什么**。它必须是可声明的、随项目走的，形态照 §3.9 断言库：

```
ReadyProfile {
  project: string
  services: Array<{
    name: string                       // compose 服务名 / 容器名
    expect: 'running'                  // 容器层
    ready: {                           // 就绪层：三选一
      logPattern?: string              // 如 Spring Boot 的 'Started .*Application in'
      httpProbe?: { path: string; port: number }
      healthcheck?: 'healthy'
    }
    timeoutMs?: number                 // 缺省取 apply 侧默认；冷启动可单独放宽
  }>
  note?: string                        // 已知噪声（照 skill §4 的口径）
}
```

**为什么不能靠启发式**：本仓自己踩过这个坑的反面——`StartedAt` 落在时间窗内 + 启动完成行**缺一不可**
（skill §3.1）。猜错的代价是「以为起来了，其实还在热启动」，然后一系列假阴性。

**与 §3.9 的关系**：两者同构（都是**项目内文本清单 + DSH 侧只读 + 缺省即无**）。
可以合并成一个 `verify/` 目录下的两类文件，共用加载与校验逻辑——**但就绪清单是环境面、断言库是数据面，
归属不同包**（见 §16）。

**风险**：`env_down` 是**破坏性**的（停服务会影响正在联调的同事）。所以它与 docker 的
`allowMutations` 同档：默认只给 `env_status` / `env_wait`（只读），`up` / `down` 走能力闸门 +
二次确认。**默认连 `up` 都不给**——先让人手工起，工具只负责「等就绪」与「看状态」也可以成立。

### 13.1 同一台机器上的两条容器写入口：口径（2026-10-03 定，根 ROADMAP 第 10 项）

**问题**：`docker` 的 `allowMutations` 与 `devenv` 的 `writeCapability` 都能启停容器。前者是
**插件级**开关——一开就能对**任意**容器 `start` / `stop` / `restart` / `remove`；后者守着
「**清单就是白名单**」。两条路并存时，后者那道白名单**可以从旁边绕过去**：agent 不必碰 `env_down`，
直接点名容器调 `docker_action` 就行。

**先把两边的门读准**（比「同档」这句话精确得多）：

| | docker `allowMutations` | devenv `writeCapability` |
|---|---|---|
| 粒度 | **插件级**（该目标上全部容器） | **每目标** |
| 授权来源 | 启动环境 `DSH_DOCKER_ALLOW_MUTATIONS` **或就地提权**（面板开关 → 免重启生效） | **只认**启动环境 `DSH_DEVENV_WRITE`（无客户端半体 ⇒ 没有就地提权这条路） |
| 作用面 | `start` / `stop` / `restart` / **`remove`** 任意容器（`exec` 另有 `allowExec`） | **只在清单里声明的**容器上 `start` / `stop`；`env_up` 不创建容器 |
| 逐次确认 | 代码层没有；`remove` 的确认在**面板 UI** 与工具描述里 | **每次调用**都要 `confirmed: true`（`[CONFIRMATION_REQUIRED]`） |
| 持久审计 | 进宿主日志，没有落盘口径 | **写类要求 `auditFile`**（`[AUDIT_NOT_DURABLE]`），一条 JSON 行 / 调用 |

**定下来的口径（选「部署纪律」，不选「让 docker 也认清单」）**：

1. **一台共享机器上，只在一边开门**。要在意 `devenv` 的白名单，就**别开 docker 的
   `allowMutations`**，也**别**走它的就地提权（后者免重启生效，最容易在「临时看一眼」时被打开：
   它不需要记忆、也不需要谁来确认）。
2. **代价写清楚**（这是这条纪律贵的地方）：关掉之后，那台机器上**没有**面板的启停按钮、
   没有 `docker_action`、也不能 `remove` 容器；一次性排障要看容器只能读（`ps` / `logs` / `stats` /
   `inspect` / `events`），要动手就得走 `devenv`（即：把它写进某个项目的 `ready/<项目>.ready.yaml`）
   或者人上机器敲。**换句话说：白名单是一种选择，不是默认状态**——想保它就别在旁边开一扇更宽的门。
3. **为什么不选另一条路（让 docker 的变更面也认同一份清单）**：`docker` 的面板是**通用排障**面，
   「重启一个任意容器看看」正是它存在的理由；把它绑到「某个项目的清单」上，要么让排障退化成
   「先去写一份清单」，要么得再造一个「临时放行清单」的概念——而那正是 `devenv` 白名单要防的
   **第二套真相**。真要合，合的方向是**一处声明、两处生效**（像 tty 连接簿那样），那要连同
   `allowMutations` 的发布语义一起改，属另一个量级的决定。
4. **什么时候该重新审这条**：一旦出现「同一台机器上两边都必须开」的真实需求。那时先问一句
   「这台机器上到底谁该有权动容器」，再决定是把它上收成 `kit` 里的**共享作用域来源**，
   还是接受「有人确实需要通用排障」并把白名单降级成**提示**（后者意味着 `devenv` 的那道门
   不再是安全边界，只防手滑——那就必须如实这么写）。
5. **这条规矩目前只有文档，没有守卫**（诚实标注）：它约束的是**人的部署动作**，不是仓库内容；
   能被守卫化的是第 3 条那条「合并」方向（届时需要一条「同一目标上不许出现两条容器写入口」的
   配置判据）。今天没有这种东西可守——写在这里，是为了下次有人想两边都开时先看到代价。

## 14. PR 流程（2026-10-01 结论：**不自研**）

agent 写完代码后的真实下一步是开 PR、看 CI、读 review、改、再推。这一环现在是断的。

**但正确做法不是写插件，而是接官方 MCP 服务器**：GitHub / GitLab 都有官方（或成熟）MCP server，
这**正是 dsh-mcp-config 的场景**。自研一套没有理由——「不用自研」这个判断本身有本仓先例：
`packages/docker` 就是「不自建连接簿界面，读 tty 的」。

**落地**：不进本方案范围，走 `~/.dsh/cordis.patch.yml` 的 MCP 托管区块挂对应的 MCP server，
在 插件配置 → MCP 服务器配置 卡片里维护。**本文只记「已识别、决定不自研、走 MCP」这一个结论**，
避免下次又把它当成缺口重新评估一遍。

### 15.2 工具面

> **工具名前缀是 `site_` 而不是 `web_`**（2026-10-01 改）：宿主自带的
> `@deepseek-ai/dsh-tool-web` 已经占了 `web_search` / `web_fetch`（**公网**检索与抓取）。
> 两者同前缀而域完全不同——一个是公网 HTTP 客户端，一个是内网站点的真浏览器。
> 最危险的一条误选路径是：**SPA 用 `web_fetch` 拉回来是个空壳**（JS 没执行），
> 模型据此判断「页面坏了」，而那正是本插件要消灭的**假阴性**。
> `site_` 与配置词汇（`targets` = 站点）一致，且不与 `ui_*`（GUI 自己的插件 id）撞族。

| 工具 | 作用 | 输出契约里的坑 |
|---|---|---|
| `site_open [url]` | 打开页面（可用已验证的站点会话）。**不给 `url` = 打开站点根**——站点已声明且已过同源判据，逼调用方再抄一遍 URL 不换来任何安全性 | 只允许同源 + 声明路径前缀内 |
| `site_shot [path]` | 截图（返回真 PNG 落盘路径，agent 可直接看） | `path` 必给；`width`/`height` 可选 |
| `site_click <selector>` | 交互（登录、点查询）。**只按 CSS 选择器**，不做按坐标点击 | 回显键是 **`selector`**；**动手前核当前页面源**，异源被拒（§17.13.3） |
| `site_fill <selector> <value>` | 填值（派发 `input` + `change`，前端框架能感知） | 回显键是 **`selector`**；同样核当前页面源 |
| `site_console` | 收集 console 消息并三档分类 —— **发布后最常见的前端故障信号**。错误与告警的**正文**都给出来，噪声按规则给出构成 | `errors`/`warnings`/`noiseRules` 都是数组，另有三个计数 |
| `site_text` | 取页面**可见文本**（不是 HTML） | 末尾**始终**附「全文 N 字符（未截断）」或「已截断：本次返回前 N 字符，全文 M 字符」 |
| `site_verify [project]` | **按项目清单跑一批断言**（`web/<项目>.yaml`，2026-10-04 加）：同一个 URL 的多条断言共用**一次观察**，逐条给三态与依据。只做「打开 + 观察」——不点击、不填值、不跟随链接 | 「没验成」（页面打不开 / 观察失败，进 `problems`）与「验出问题」分列；一页出问题只砸那一页；整体性问题（清单读不到 / 没有这个 target 的断言）在**碰浏览器之前**报出来 |

> **2026-10-02 端到端实测（第一轮真机验收）**：上表「输出契约里的坑」一列是被真机打出来的。
> `site_click` / `site_fill` 曾把判定层的返回写成 `{ clicked }` / `{ filled }`，而工具声明的是
> `{ selector }` + `additionalProperties: false` —— 后果是**浏览器动作真的生效了，但工具调用报
> `invalid output`**。这是最坏的一类失败：agent 会以为没点成，于是去重试一个有副作用的动作
> （真实环境上可能就是重复提交）。四条的完整记录见 §17.13。
> **现在有一道守卫**：`packages/devfront/test/tool-contract.test.ts` 按同一张表把「声明的 schema」
> 与「实际产出的键」对起来，并检查渲染层读的字段真的有值。

### 15.3 边界（必须写清，否则会变成一个通用浏览器自动化工具）

- **它是「验证」工具，不是「自动化」工具**：不做定时任务、不做爬虫、不做批量操作。
  **`site_verify` 是这条边界上唯一的一批**，判据是**集合由谁给出**：
  要访问哪些页面只能来自项目清单里**逐条写死**的 `assertions[].url`（不发现、不跟随链接、不猜 URL），
  且每个 URL 都要过 `site_open` 那道同一套判据——「批量开页面」指的是**工具自己发现**一组页面，
  那不做（2026-10-04 把这条口径写明，见 [devfront 记-28](../packages/devfront/ROADMAP.md)）；
- **登录凭据与站点会话**走 `resolveSecret` 口径（§3.7-1），且**只对已在 `scopeDirs` 内的目标**。
  **2026-10-04 落地**：`site_fill` 的值二选一——明文 `value` 或**凭据引用** `credentialRef`
  （`env:NAME`），后者**只认目标 `credentialRef` 声明过的那一个**（「能读任意环境变量」与
  「能读这一个」是两回事），值由官方凭据服务解析，**不进返回 / 会话记录 / 审计**；返回里带
  来源保护强度（今天 provider 给的几层全是 `none`：agent 与用户同 uid，读得到——**方便，不是
  防护**）。剩「按声明的登录步骤自动走一遍」那种编排没做，见 `devfront` 记-29；
- 与 §3.9 断言库同构：**前端验活也应是可声明的断言**（URL + 期望文本/元素），
  而不是每次让 agent 现编操作序列——否则同样不可积累、不可复审；
- **每个动作进审计**（§5 审计面口径）。

> **2026-10-01 落地进展**：§15.2 的**判定层与 CDP 驱动**都已在 `packages/devfront` 落地
> （动作白名单、站点范围、console 三档分类、前端验活断言、真 Chrome 驱动），
> 见 [该包的 ROADMAP](../packages/devfront/ROADMAP.md)。
> 归属已定：Chrome 客户端从仓根 `scripts/chrome-cdp.mjs` **上收进 `kit`**（`chrome-cdp`）——
> 它有 5 个消费者跨两个包，放在任何插件包里都会让根 `scripts/` 反向依赖插件。
> 六个 `web_*` 工具已注册进宿主（未启用 / 未配站点时一个都不注册）。
>
> **一处实现中的判断**：§15.3 说「与 §3.9 同构」指的是**清单形态**（项目内文本 + DSH 侧只读 +
> 缺省即无），**不是预期算子**。DOM 上用 `toContain` / `elementExists` / `elementText` / `consoleClean`；
> 把 `gte` / `rowCount` 搬到 DOM 上没有意义，把 `toContain` 搬到结果集上又要先决定「比第几列」
> ——那是数据面已经解决过的问题。所以两套算子**刻意不合并**，有用例钉住这件事。
>
> 另有一处**刻意不合并**：环境就绪判据（`devenv` 的 `env-ready.ts`）与前端断言看着都能挂在「一个服务的页面」上，
> 但就绪是**等待期**判据、断言是**验证期**判据——合并会让「页面还没渲染完」被报成「验证失败」，
> 而那正是 §15.1 说的假阴性来源。（2026-10-02：这段原先写的是「`devdata` 的 `env-ready.ts`」，
> 那是它暂住 `devdata` 期间的路径——归属迁走了，**指路的句子要跟着改**，否则下一个人会去
> 一个已经不存在的路径找它。）

## 16. 包结构：**已定三包**（2026-10-01 拍板）

原方案（§7）判断是「**一个包，不做聚合**」。追加 §13 / §15 之后重新做了这个判断，因为：

| 面 | 主要依赖 | 与数据面的关系 |
|---|---|---|
| 数据面（§2–§3） | SSH 通道 + `mysql2`/`pg`/`redis` 驱动 | — |
| 环境编排（§13） | docker 通道（复用 `readTtyBooks` / `RemoteExec`） | 与数据面的 `test-isolated` **天然耦合**（起副本 = 起容器） |
| 前端验证（§15） | Chrome CDP（本机浏览器，**不经目标主机**） | 与数据面**互不相干** |

**结论：3 个包，不是一个巨型包。** 理由：

- 前端验证与数据面**没有任何共享面**，硬塞在一起只是让一个包的 README、依赖、风险清单都膨胀；
- 环境编排与数据面的 `test-isolated` 有真实耦合，但也只到「都经同一个 SSH/docker 通道」这一层；
- 本仓已有先例：耦合强的（docker 的多目标 + 多闸门）在一个包里，**互不相干的不硬合**。

| 包 | 范围 | 状态 |
|---|---|---|
| `packages/devdata` | 数据面（§2–§3）+ **验活断言库**（§3.9） | **已建**（**环境就绪判据**于 2026-10-02 迁往 `devenv`） |
| `packages/devfront` | 前端效果验证（§15） | **已建**（判定层 + CDP 驱动 + `web_*` 工具注册） |
| `packages/devenv` | 环境编排（§13）：容器 / 进程 / 端口 / 探针的状态 | **已建**（2026-10-02；判据层已迁入，观测层与工具面见 §16.1 的第 3–5 步） |

**不提前建空包**：`docs/architecture.md §2` 的包清单与 workspace 是**双向一一对应**的
（`docs-index` 判据 5），建了包就得加清单行，而一个只有骨架的包会让「这套东西现在能做什么」
这个问题的答案变模糊。所以 `devenv` 在它的观测层开工时再建，那一刻同步清单行与发布面。
> **2026-10-02 落实**：`devenv` 建包与就绪判据的迁入是**同一步**（§16.1 前置清单第 2 步），
> 所以它建起来的那一刻就带着能跑、有用例的一块——不是空骨架。

**三个包共同遵守的纪律（不因拆包而漂）**：私有包（§7 的 N1/N2/N3 处理）、agent-first（§3.6）、
能力闸门复用 kit（§3.7-1）、**不做聚合**（拆成三个再做一个聚合包是最坏的组合）。

**拆包的代价也照实记**：三个包各要本身份（README、文档档位、可能的 DEFECTS/ROADMAP、CI 接入），
且 §7 的 N1（让 `scripts/aggregate.mjs` 认 `private`）**一次要覆盖三个**。
> **2026-10-02 更正**：N1 **已经落地**（`aggregate.mjs` 的 `isAggregatable` 跳过 `private`），
> 本节原先写的「那件事还没做，目前靠『三个包都不带 `dsh.bundle.patch`』兜着」**已失效**——
> `devdata` 现在**带** `dsh.bundle.patch`（不带就装不进 profile），实测仍不进聚合包（§7 / §17.14）。

### 16.1 `devenv` 的边界（2026-10-02 定）

**判据只有一条：清单与求值跟着「它判的对象」走，不跟着实现形态走。**

理由：三个面的清单本来就是同构的（项目内文本 + DSH 侧只读 + 缺省即无），形态区分不了它们；
真正决定归属的是**观测来源**——而观测来源决定了依赖方向与失败模式（连不上库 / 容器没起 / 页面白屏
是三种完全不同的故障）。按来源分，包边界与依赖方向自然一致。

| 判的对象 | 观测来源 | 归属 | 现状 |
|---|---|---|---|
| 数据服务的**内容**（SQL 结果、key、lag） | 数据库 / 中间件协议 | `devdata` | ✅ 已在（`verify*`） |
| 容器 / 进程 / 端口 / HTTP 探针的**状态** | docker 通道 + 网络探针 | **`devenv`** | ✅ 判据（`env-ready*`）**已迁入**（2026-10-02，与建包同一步） |
| 浏览器**渲染**的结果（截图 / console / 文本） | Chrome CDP（本机浏览器） | `devfront` | ✅ 已在 |

**为什么迁移是安全的**：`env-ready*` 在 `devdata` 里**没有任何内部消费者**（只有 `index.ts` 的
re-export），593 行实现 + 394 行用例自成一体。所以「建 devenv 包」与「迁这两块」必须是**同一步**——
先建空包就违反了「不提前建空包」，先迁移则会让 `devdata` 暂时少一块已声明能力。
> **2026-10-02 落实**：这两块已经按上面这条同一步做完（实数是 593 行实现 + 394 行用例，
> 迁移时逐个 diff 核对过，除归属说明外**逐字节相同**）。`devdata` 侧已删旧文件与 re-export，
> **不留转发**——两个包同时导出同一份 API 会让「谁是归宿」重新变模糊。

**依赖方向**：`devenv` → **`kit`**（机制：连接簿读取、远程执行、能力闸门），
**不 import 另一个插件的代码**。备选方案与代价：

| 方案 | 做法 | 代价 |
|---|---|---|
| **B1（推荐）** | 把 `readTtyBooks` + `RemoteExec`/`sshTarget` 的**最小面**上收进 `kit` | 动 `kit` → 触发全仓钉版同步（12 处声明）+ `docker` 改成从 kit 取 + 守卫跟着改。**属 L0** |
| B2 | 给 `@hyzyn/dsh-docker` 加子路径导出（如 `./ssh-exec`），`devenv` 依赖它 | 插件之间出现**代码级依赖**（本仓无先例：docker 只读 tty 的**配置**，不 import 它的代码）；且等于把 docker 的内部实现变成公共 API |

判据：**共享的是「机制」（怎么连、怎么读连接簿）→ 上收 `kit`；共享的是「数据/配置」→ 读对方的
settings entry**。devfront 的 `scope.ts` 已经因为同一条理由上收到 `kit`，B1 是本仓既有的答案。

**前置清单（按顺序，每步都可独立验收）**：

1. 通道（B1 或 B2 二选一）——只有这一步是 L0；**✅ 2026-10-02 已做，选 B1**（落点见下）；
2. 建包：`private: true` + `lib/` 产物 + `docs/architecture.md §2` 清单行
   （`docs-index` 判据 5 要求包清单与 workspace 双向一致）；**与迁移 `env-ready*` 同一步**；
   **✅ 2026-10-02 已做**（`packages/devenv`；`dsh.bundle.patch` **刻意没在这一步加**——补丁指向的
   插件本体在第 3–4 步才落地，一个指向不存在模块的补丁挂载时只会变成一条「配置问题」，
   而那正是这套东西最不该制造的噪声。`devdata` 的补丁也是后补的，先例见 §17.3）；
3. 观测层：经 docker 通道取容器状态 / `StartedAt` / 退出码 / 健康 / 日志尾部 / HTTP 探针；
   **✅ 2026-10-02 已做**（`observe.ts` / `probe.ts` / `channel.ts`）；
4. 只读工具面：`env_status` / `env_wait`（**默认只给这两个**）；**✅ 2026-10-02 已做**（`plugin.ts`）；
5. `env_up` / `env_down`：走能力闸门 + 二次确认（`env_down` 是破坏性的，会打到正在联调的同事）。
   **✅ 2026-10-02 已做**——落点见 §16.1.3；**默认不注册**（没配 `writeCapability` 的目标上不存在写入口）。

**不做什么**（继续有效）：不提前建空包；不自己写第三份 SSH/连接簿实现；不做聚合；
`B1` 之前**不动** `env-ready*` 的归属（它现在能跑、有用例，迁早了只是搬箱子）。

#### 17.4.1 通路 A/B 的实测答案：**SQL Server 该走通路 A，通路 B 在这台容器上不成立**（2026-10-02）

§4 的 C1 / C3 / C4 在 248 可达之后可以零写入地回答了。三个答案都**改了方案原本的分配**：

| 问题 | 原定 | 实测 |
|---|---|---|
| **C1**：容器里有没有目标侧 CLI | 假定「容器里的 `sqlcmd`」 | ❌ **没有**：`cdqas-sqlserver` 里 `sqlcmd` / `isql` / `bsqldb` 都没有，`/opt` 只有 java（镜像就是 `eclipse-temurin:8u482-b08-jdk`）。**通路 B 对 SQL Server 不成立** |
| **C3**：目标库的监听地址与端口 | `docker exec <c> netstat -lntp` | ⚠️ 取法要换：**这些镜像里没有 `netstat` / `ss`**。可行的是读 **`/proc/net/tcp6`**（IPv4 socket 也在那张表里，小端十六进制）。由此解出：应用有 3 条已建立连接指向 **`192.0.2.247:1433`** |
| **C4**：DSH 宿主到这些主机是否直连可达 | 待答 | ✅ `curl` 实测：`192.0.2.247:1433`（**库**）、`192.0.2.248:22/8109`（应用）**都直连可达**；`192.0.2.161:22` 可达但 **`8344` 不可达**（那台防火墙只放 22）——所以**161 上宿主机的库要走隧道**，248/247 上的直连即可 |

**结论（要改方案的分配）**：

1. **SQL Server 归通路 A**（DSH 宿主直连 `192.0.2.247:1433` + `tedious` 纯 JS 驱动），**不是通路 B**——
   方案把它归通路 B 的依据是「**无可用的纯 JS 驱动**」，而**那句是错的**（`tedious@20.0.0` 实测纯 JS）。
   原判断把「库在容器里、只能从目标侧访问」当成了默认，而这里的库是**网络上独立的一台**。
   ⚠️ **代价（实测分量，2026-10-02）**：把 `tedious` 装进空目录 → **131 个包 / 65 MB**，
   其中 **`@azure/*` 占 42 MB（约 65%）**——那是 Azure AD 认证，**走 SQL 账号认证时完全用不到**。
   而且**没有任何版本能避开**（`9.2.3`/`11.0.8` 带 `@azure/ms-rest-nodeauth`，
   `15`/`16`/`20` 带 `@azure/identity` + `@azure/keyvault-keys`）——**这不是版本问题**。
   所以真正要定的是：**为了 SQL Server 接受一个 65 MB 的依赖树，还是换路子（通路 B 得先解决
   「哪台机器上装客户端」，或干脆不做 SQL Server）**。

### 17.7 P3 第一件：SQL 只读面（2026-10-01）

落 `src/sql.ts`：**语句分类 + 结果整形 + 上限收紧 + 兜底分页注入**（纯逻辑，27 条用例）。

分类判据是**结构**不是关键字黑名单——先扫出「每个字符是否处于代码态」的掩码（行注释 / 块注释 /
单双引号字符串 / 反引号 / 方括号标识符），再按**第一个代码态字符**取关键字判定：

| 判据 | 结果 |
|---|---|
| `SELECT` / `WITH` / `SHOW` / `DESCRIBE` / `EXPLAIN` / `VALUES` / `TABLE` | 放行 |
| 已知写 / DDL / 权限 / 事务控制 | 拒（`NOT_READ`，文案说清「本档永久只读」） |
| 顶层分号之后仍有代码 | 拒（`MULTI_STATEMENT`） |
| 注释 / 字符串未闭合 | 拒（`UNTERMINATED`） |
| **其他一切** | 拒（`UNKNOWN_STATEMENT`）——**不认识就不放行** |

**实测抓到并修掉的一个真 bug**：初版语句头只按**空白**跳过，于是前导注释里的 `/` 被当成
非空白、正则在原始串上匹配失败——`/* SELECT */ DELETE FROM t` 被判成「不认识的语句类型」
而不是「这是写操作」。**拒绝的方向是对的，但理由与恢复指引都错了**（会让人以为是语句类型问题，
实际是写操作）。修法：语句头定位改为按**掩码**跳过非代码态字符。留了三条回归用例。

另外明确了两处**不追求完备**的地方（写进注释，不假装）：
`materializeLimit` 只认顶层 `LIMIT` / `FETCH` / `TOP`，不解析嵌套子查询的分页，也不判断已有上限
是否比策略更宽——真正的硬保证是「按 `effectiveLimit` 限行」+「计划护栏执行前拦截」这两层；
多余空语句（`SELECT 1;;`）不算多语句（判据是「分号后还有没有代码」，不是分号次数）。

### 17.8 P3 第二件：工具注册表（2026-10-01）

落 `src/tool.ts`（23 条用例）。核心是把「工具清单」与「操作矩阵」从**两处各写一份**变成**一处派生**：

```
可见工具 = 注册表 ∩ 矩阵受管动作 ∩ (目标允许的档位) − 矩阵 never
```

于是 §3.6 里「有入口的白名单在 `FLUSHALL` / `EVAL` 面前是装饰」这句话**变成了可执行断言**：
用例对每个引擎断言「可见面 ∩ never = ∅」「可见的引擎专属项都来自受管动作」。

配套的接线是 `invokeTool`（**先裁决，再执行**）：

1. **可见性**：不可见的工具直接拒，且**不进入执行路径**（用例断言执行器零调用）；
2. `adjudicate`：环境 / 作用域 / 矩阵 / 能力；
3. 执行 → **写审计**。

**审计记的是「试过什么」**：放行、被拒、不可见、越界**四种都记**（用例逐个断言），
并带 `operationId` 便于把一次操作串起来。审计 sink 抛错时**不吞掉**（本内核不替调用方决定
「写不进去怎么办」，但绝不允许「操作照做、记录没有」）。

**两条刻意的不对称**：`never` 的动作**不注册**（不是注册了再拒）；写 / 危险读**默认不露入口**，
且**未接入闸门也不露**（防止「配了一半」的目标把写路径露出去）。反过来，**读类始终可见**——
可见性与可执行性是两件事，`unknown` 环境下读类照样看得见，执行时由 `adjudicate` 放行。

**实现中发现的一处注册表缺项**：初版只登记了 `query` / `search` / `sample` 这类通用动作，
**漏了 `get` / `info` / `keys` / `set` / `del` / `expire` / `monitor`** 这些 Redis 档的单个操作——
于是那些能力在工具面上根本没有入口。已补，并定下命名口径：**引擎专属操作就用矩阵里的动作名，
只有跨引擎同义的动作才用通用名**（`search` / `sample`）。

### 17.9 P3 第三件：查询计划护栏（`src/plan-guard.ts`）

这是 agent 场景里**最值的一道护栏**：agent 最典型的失败不是「写错」，而是**忘记加 `WHERE` 的
SELECT**——它不改变任何东西，只读护栏完全放行，代价却可能把共享联调库扫穿。
**行数上限管的是「回来的行数」，管不了「扫描的行数」，两者不是一回事。**

判据是**按引擎语义分派**，因为同一个词在不同引擎里代价相反：

| 计划文本 | 判成 | 为什么 |
|---|---|---|
| `Seq Scan` / `Table Scan` / `type: ALL` | 全量 | 所有引擎都成立 |
| PostgreSQL 的 `Index Scan` | **不算全量** | 它既用于扫全表也用于定位一行，行结构相同——**赢面在估算行数，不在操作名**，交给阈值判 |
| SQL Server 的 `Index Scan`（无 seek） | 全量 | 是扫全量的可靠信号 |
| MySQL 的 `type: index` | 全量 | **除非整份计划里有 `Using index`**（覆盖索引读索引本身，便宜） |

**「拿不到计划」一律拒**（`PLAN_UNAVAILABLE`），不是「跳过护栏」；**「不认识的计划」也拒**
（`PLAN_UNRECOGNIZED`）——不知道代价就放行，等于没有护栏。两条都不受阈值影响：
把阈值调成 `undefined` 不能绕开全表扫描判据。

**阈值语义**：`maxRows` / `maxCost` 都是可选的，且**「未配置 ≠ 零容忍」**——
不配 = 不做这一层检查，配 `0` = 一行都不许。

**实施中改掉的三处判据错误**（都留着用例）：

1. `Clustered Index Scan` 被当成便宜——**SQL Server 的 index scan 本就是扫全量**，
   我按 PostgreSQL 的语义误判了；
2. `Using index` 既是「便宜」信号又是「不走全量」的排除条件，而我把便宜判定放在全量之后，
   **它永远没机会生效**；
3. `type: index` 与 `Extra: Using index` **在计划里是两行**——逐行判拿不到跨行上下文，
   覆盖索引信号必须**先整份算一次**。

护栏已接进 `invokeTool`：**拒跑发生在执行之前**（用例断言执行器零调用），且只对 SQL 的
`query` 生效（`explain` 自身不过护栏，否则递归要计划）。

### 17.10 P3 第四件：只读自证（`src/readonly-probe.ts`）

SQL 档**唯一的硬护栏**。关键在于**它自己不能去试写**——「试一次写，失败即证明只读」是最直观的
做法，也是**不能用**的做法：在共享环境里试写，**成功就是真的写进去了**。

所以自证只读**权限元数据**（`information_schema` / `pg_has_role` / `IS_MEMBER` / `USER_TAB_PRIVS`），
由引擎实现填 `ReadOnlyFacts`，内核只做判定。判据顺序是契约：

1. 引擎不支持（Redis / RocketMQ 没有账号级只读概念）→ `ENGINE_UNSUPPORTED`；
2. **超级用户 → 拒，且这条排在账号证据之前**——超级用户绕过权限检查，即便报「只读」也不可信；
3. 明确可写 → `ACCOUNT_WRITABLE`；
4. **拿不到证据 → `EVIDENCE_MISSING`（缺证即拒）**。

一条诚实的边界：`session_read_only`（如 PG 的 `BEGIN READ ONLY`）是**连接级**事实，
不等价于账号级只读——所以它只作**附加层**如实报告，不让它单独构成「已自证」。
方向与 `credential.ts`（认不出按「不防护」处理）、`env.ts`（不认识回落 `unknown`）一致。





### 17.11 P6 一件：Redis 命令解析（`src/redis-command.ts`）

矩阵管的是「某一族允不允许」（`get` 放行、`keys` 要单独授权、`set` 要写授权），本模块管的是
**这条具体命令属于哪一族、它动的是哪个 key、`SCAN` 的 `COUNT` 有没有被夹紧**。

**这一档比 SQL 更需要解析层**：SQL 有库账号兜底（代码写错也翻不了车），
**Redis 没有只读账号这回事**——一条连接读写同权，「受限」只能靠白名单，**漏判没有第二层网**。

三条判据（与 SQL 侧同源）：

1. **未登记的命令一律拒**——不认识的命令被放行就是一条没被审过的路径；
2. **`SCAN` 的 `COUNT` 只能收紧**——候选可请求更小，请求更大被夹回策略上限。理由与行数上限相同：
   `SCAN` 是这一档**唯一的遍历手段**（`KEYS` 被单独授权），一次 `COUNT 1000000` 等于把整个
   键空间拖进上下文；
3. **写命令必须解析出目标 key**——审计里写不出「改了什么」的写操作不放行。

一处刻意的按参数分档：**`INFO ALL` 是危险读，`INFO memory` 是普通读**——同一个命令判得不同，
在 Redis 侧是常态。

**实施中抓到的一处真 bug**：`HSCAN` / `SSCAN` / `ZSCAN` 的**第 1 个参数是 key**（光标在第 2 个），
而 `SCAN` 是光标在第 1 个。初版按 `SCAN` 的布局统一处理，于是带 key 的三个变体全被拒。
用例把两种布局都钉住了。

**仍待接线**（见 ROADMAP 待办 C9）：工具参数现在是结构化的（`set key value`），而解析层吃的是
**命令原文**（`SET k v`）——要让 agent 直接发命令，得在工具层加一条「命令原文」入口，
由内核先解析出动作名再裁决。

> **2026-10-01 已接线**（见 §17.12）：入口是 `invokeRedisCommand`。上面的判断在当时是对的，
> 但接线时发现了一个比「少一条入口」更硬的问题——**矩阵按动作名分档、解析层按参数分档，
> 两者会在 `INFO ALL` 上差一档并静默从松的那一档放行**。这一条是接线时抓到的真漏洞，不是设计里的已知项。

### 17.12 C9 接线：Redis 命令原文入口（`invokeRedisCommand`）

**为什么必须有这条入口**：结构化参数把「是哪条命令」交给了调用方，而解析层才是那道白名单。
只留结构化入口，等于让 agent **从白名单旁边绕进执行器**（直接构造 `{ action: 'del', key }`，
解析层永远看不到那条命令）。原文入口让「命令 → 动作 → 闸门」的映射由内核自己算。

**接线时抓到的真漏洞（本节的主要价值）**：矩阵的键是**动作名**，解析层的档位由**参数**定——
`INFO ALL` 与 `INFO memory` 都映射到动作 `info`，但前者一次吐出全部节（含客户端与命令统计），
解析层判它是`read-dangerous`。而矩阵里 `info` 是普通读，于是裁决层按 `info` 分档 →
**危险读能力闸门根本没走**，`INFO ALL` 直接放行。这正是 §3.6 那条失败模式「从旁边那条路绕过去」，
只不过绕法是「同一个动作名下按参数分档」。

**修法（三处，缺一漏洞就还在）**：

1. `OperationRequest.operationClass`：调用方可以报「更严的档位」，语义是**只能更严不能更松**
   （`stricterClass` 取排序更严的那一个）；
2. `adjudicate` 按**实际生效**的档位分档，`capabilitySpecFor` 也按它取能力——
   否则升级过的命令在这里又退回普通读；
3. `hintFor` 同样吃生效档位：撞闸门时给出的授权指引必须指向**危险读**能力，
   否则 agent 拿到的指引指向别处，只能原样重试（§3.6.1 的实现要求 2）。

**执行器必须照 `raw` 下发**：解析层审的是原文，若执行器照结构化字段重新拼一条，
「审过的」与「跑了的」就成了两份字符串（TOCTOU 缝）。所以 `commandArgs` 给的字段是
**裁决与审计用的上下文**，不是重建命令的配方。

**顺带修掉的一处错诊断**：不可见的动作原先一律报 `UNCLASSIFIED_OPERATION` + 「不在受管动作里」。
但写类在 `unknown` / `production` 下本来就被藏起来（它在矩阵里登记得好好的），
报「未登记」会让 agent 去改动作名——一个不可能有结果的方向。现在按实际原因分：
`never` → `OPERATION_FORBIDDEN`、环境不许写 → `ENV_NOT_WRITABLE`、没接闸门 → `CAPABILITY_NOT_DECLARED`、
真未登记 → `UNCLASSIFIED_OPERATION`。解析层的 `FORBIDDEN_COMMAND` 也不再被报成「不认识」——
**「被明确排除」与「打错字」是两件事**，agent 该做的事完全不同。

### 17.13 devfront 第一轮真机验收：四个缺陷（2026-10-02）

第一轮端到端验收（本地零依赖夹具 + 六个工具全跑 + 三组对照实验）**判定这套工具面可用**，
但抽出四个缺陷。四个都不是「实现没写」，而是**实现与它自己声明的契约/注释相反**——
这类缺陷单测抓不到，因为它们恰恰把矛盾一起写进了断言。

| # | 缺陷 | 为什么危险 | 修法 |
|---|---|---|---|
| 1 | `site_click` / `site_fill` 判定层返回 `{ clicked }` / `{ filled }`，工具声明 `{ selector }` + `additionalProperties: false` | **动作生效但报 `invalid output`**。agent 以为没点成，会重试一个有副作用的动作 | `page.ts` 回显 `{ selector }`；渲染层读 `selector` 也随之恢复 |
| 2 | 拒绝码 `OUT_OF_SCOPE` / `SITE_NOT_ALLOWED` **没被带出去**（只抛中文正文） | 码是唯一的稳定标识符，却只活在单测和审计日志里，agent 只能正则猜散文 | 抽 `denialMessage()`：格式 `[CODE] 正文` + 另起一行「恢复路径：」 |
| 3 | `console.log/info/debug` 被归成 `warning` | 干净页面只要打过一行日志，摘要就报「告警 N」——**误报**，正是「噪声淹掉信号」的成因 | 归 `noise` 档（留在报告里、不计入信号） |
| 4 | `site_console` 只给告警**计数**、不给正文 | 「记下来了但不让人看」；agent 看到「告警 1」无从下手 | 输出增加 `errors` / `warnings` 正文数组（各截前 10 条）与三个计数 |

**缺陷 3 的判据是注释与代码互相打脸**：`console.ts` 那行的注释写着「信息类：不是错误，**也不构成告警**」，
下一行 `return { class: 'warning' }`；同档用例的名字也写着「不构成告警」，断言却写 `'warning'`。
**用例把 bug 一起抄了进去**——所以「有测试」不等于「有守卫」，守卫要校验的是**契约**，不是实现的当前行为。

**缺陷 1 的成因是覆盖缺口，不是疏忽**：上一版冒烟只跑了 `open` / `text` / `console` / `shot`，
**没跑 `click` / `fill`**。教训不是「补两条用例」，而是：
**声明的契约与实际产出的键之间没有任何东西在维持一致**——它们住在两个文件里，靠人脑对齐。
所以这次补的是**表驱动的契约守卫**（`test/tool-contract.test.ts`，12 条）：
把每个工具的 `output.schema` 与走真实合成路径产出的对象对起来，并检查渲染层读的字段真的有值
（只检查「有没有抛」不够——渲染读错键会渲染出一段**看着成功、其实空掉**的话）。

**另有一条设计矛盾同轮暴露**：devfront **没有客户端半体**，当时据此记下「GUI 里没有 devfront 的
配置面」——**那句话是错的**，更正与修法见 §17.13.5。错因值得单独记一笔：我拿**本仓 kit 自己的**
函数名 `suppressAutoSettingsPage` 去搜整份 DSH 安装，搜不到就断言「本版本没有自动生成设置页的
机制」，而 DSH 那边的入口叫 `settings.configure({ auto })`——它一直都在。**靠搜错字符串得出的
反向结论**比没有结论更危险：它看起来像一条已验证过的事实。

#### 17.13.1 第二轮验收：又把两个**同类**漏网挖出来（2026-10-02）

第一轮修完四条后复验（15 次调用）**全部通过**，但验收方指出「有几个数我拿不到/没法核对」。
一查，其中两条是**同一个缺陷类的镜像版**——声明了却拿不到，而这正是第一轮修的那四条的病根：

| # | 缺陷 | 为什么是同一个病 | 修法 |
|---|---|---|---|
| 5 | `site_text` 的 `truncated` / `length` 声明在 `output.schema` 里，但渲染层**只在截断时**才写出来 | agent 只看得到 `render()` 的输出 → 两个字段**永远拿不到**；而且「没截断」变成**靠缺席表达的信号**（agent 得先知道这个约定） | 渲染末尾**始终**附一行：`—— 全文 N 字符（未截断）` / `—— 已截断：本次返回前 N 字符，全文 M 字符` |
| 6 | `site_console` 只给噪声**计数**，不展开构成 | 被排除的东西**不可核对**：噪声规则一旦误伤真错误，它会静静地把它吞掉——而「噪声不能淹掉信号」正是这套东西的立身之本 | 输出加 `noiseRules`（`favicon-404 ×1` 这种），渲染加一行「噪声构成：…」；信息类日志也补上规则名 `page-log` |

**教训（比缺陷本身值钱）**：修完一类缺陷之后，要**回头找它的镜像**——
「声明的契约」与「实际交付给 agent 的东西」是两端，第一轮只查了「产出 ≠ 声明」（
`clicked` vs `selector`），没查「声明了 ≠ 交付了」（`truncated`/`length` 声明了但渲染不出来）。
守卫因此也扩了两条：渲染层**始终**可见 + 噪声构成**可核对**。

#### 17.13.2 同轮补验的三件事 + 两条边界（2026-10-02）

验收方列的「未验证」里，三条现在有了结论，两条是**记录边界**而不是缺陷：

- **`site_fill` 到底派发了哪些事件** —— 用一页只监听事件名的夹具实测：**`input` 与 `change` 都派发**
  （页面显示「已触发：input, change」）。此前只能从「查询结果出现了」反推监听器收到了值，那不够。
- **「全文 4468 字符」有没有独立来源** —— 有：用 kit 的 `Chrome` 客户端**另开一条 CDP 通路**读
  `document.body.innerText.length`，独立测得 **4468**，与工具自报一致；返回正文正好 4000 字符。
- **噪声计数在同一浏览器会话里不稳定** —— 首次访问 `噪声（已排除）2`（favicon 404 + 页面自己的
  `console.log`），**再次访问只剩 1**：Chrome 缓存了 favicon 的 404，第二次不再发请求。
  **推论：`噪声数 == N` 不能当断言写**（会随机红）。可以断的是 `本站错误 == 0`，
  以及 `noiseRules` 里出现了预期的那条规则。
- **边界一（已收紧，2026-10-02 第二轮验收）**：`open` 的闸门只管「打开的那个 URL」，
  管不了页面自己跳去哪——夹具里一页 `location.replace()` 到另一个源，`open` 时它合法（URL 在同一源内）。
  **这道边界原先只被记成「跳到哪管不了」，没有写明它同时放行了写**，而实测是：
  跳转之后 `site_click` / `site_fill` 在异源页上**无差别生效**（异源页真的被改动了）。
  也就是说「审查入口」实际退化成了「审查入口，**除非页面自己把你带出去**」——
  任何声明站点上的一个跳转（登录 / SSO / 第三方重定向 / 被投毒的页面）就能换来对任意源执行点击与填值的能力。
  **修法（见 §17.13.3）**：读放行、动手不放行。
- **边界二：iframe 的内容读不到** —— `document.body.innerText` 不含子文档，
  所以跨源 iframe 里的文字**进不了** `site_text`。这一侧是被结构性排除的，不是靠规则挡的。

#### 17.13.3 跨源动作闸门：读放行，动手不放行（2026-10-02）

**怎么发现的**：第二轮验收的验收方在核 §17.13.2 那条边界时，发现实际放行的**不只是读**。
它做了两个探测，证据链是：

```
① site_open http://127.0.0.1:8900/          → [SITE_NOT_ALLOWED]   ← 入口拦死
② site_open .../redirect.html（合法）→ 页面自己跳到 8900
   site_text → FOREIGN ORIGIN PAGE                              ← 读放行（设计使然）
③ site_click body → 已点击 body                                ← **写也放行，没有任何拒绝**
```

它的判词值得原样记下来：

> 读异源内容我是当作**不受信的输入数据**处理的；但对异源页**动手**是另一回事。
> 「审查入口」变成了「审查入口，除非页面自己把你带出去」。

这个判断是对的，而且**我原先的设计里根本没有这一条**——origin 判据写在
`if (action === 'open')` 里面，其余动作压根没有 origin 判据。这不是「文档没写清」，
是**漏了一道闸门**。

**修法**（按验收方的建议，唯一一处它接受的做法）：

| 面向 | 处理 |
|---|---|
| `open` | 不变：入口必须同源 + 在声明路径前缀内 |
| `text` / `shot` / `console`（读） | **放行**：登录跳转后读页面、截图是登录流程的必要部分；读到的东西按不受信数据处理 |
| `click` / `fill`（动手） | **执行前核「当前页面」的源**，不在允许集合内一律拒，码 `PAGE_ORIGIN_NOT_ALLOWED` |

**三个实现上的要点**（每一个都有用例钉住）：

1. **必须实时问浏览器，不能在判定层静态判。** `adjudicateWebAction` 是纯函数，看不到浏览器；
   而驱动自己记的 `lastUrl` 是「上次导航到哪」，**客户端跳转不会更新它**——那恰好是这道判据要防的东西。
   所以 `WebDriver` 新增 `currentUrl()` 这一条**事实**接口，由判定层决定拿它干什么（层次不能倒）。
2. **源必须显式声明才放行。** 新增 `WebTarget.allowedOrigins`（缺省 `[]` = 只能**在声明源上动手**）。
   为什么需要它：登录 / SSO 会跳到 IdP，而**填账号密码就是在那个源上动手**——
   只允许声明源会把登录流程整条掐掉。代价不能由规则偷偷承担：写下一个源，是一次值得看一眼的决定；
   **页面自己跳过去不构成授权**。
3. **读不到当前页面的源 = 拒绝。** 不知道在谁的页面上就不动手（fail-closed）；
   配置里解析不出来的 origin 条目**不授予任何权限**，免得一条写错的配置变成一次静默放行。

**端到端复验**（同一夹具、真 Chrome）：异源页上 `site_click` 与 `site_fill` 现在都返回
`[PAGE_ORIGIN_NOT_ALLOWED] 当前页面在 http://127.0.0.1:8900，不在允许动手的源里（允许：http://127.0.0.1:8899）`，
**异源页没有被改动**（修复前是被改动的）；而**读仍然放行**，同源上的点击与填值不受影响。

**顺带把 `site_fill` 也测了**：验收方只测了 `click`，并声明「`fill` 我按同一通路推断，但这是推断不是证据」。
补测结论：修复前 `fill` 同样放行（同一个缺陷的两条出路），修复后同样被拒。

#### 17.13.3-1 第四轮：把这条闸门问到边（2026-10-02）

收紧了之后，验收方列了五条「相关但没验证」，其中第一条是**对的做法**：它说
「错误里那条恢复路径，我**没有真去改配置**再回验——所以『这条路走得通』目前只是**读到的文字**，
不是实测」。一条走不通的恢复路径比没有还坏（agent 会照着它去改配置，然后再失败一次）。
五条一次测完，结论都是好的，另有两条**语义**值得写下来：

| # | 追问 | 实测结论 |
|---|---|---|
| ① | `allowedOrigins` 那条恢复路径真走得通吗 | **走得通，且动作真的落到页面上**（用只监听 `input` 的异源页做哨兵：填完之后哨兵被触发）。不是「放行了但没做事」 |
| ② | `site_shot` 在异源页上也放行吗 | **放行**（1440×757 真 PNG）。此前只有推断 |
| ③ | 多 target 会不会互相影响 | **不会**：同一页面、同一浏览器，换个 target 判决就变——授权按**调用里的 target** 查 |
| ④ | 异源页上二次导航有无残留状态 | **没有残留**：回到本站动手恢复放行；再跳一次异源又被拒（每次按**当前页**重判） |
| ⑤ | iframe 内元素被点时算哪个源 | **这个问题不存在**：`querySelector` 不下钻子文档 → iframe 内的元素**结构性不可达**（报「选择器没命中任何元素」，且 iframe 内部确实没被改动）。点 `iframe` **元素本身**判**顶层源** |

**语义一：授权按「调用里的 target」查，页面状态是全局的。** 一个插件实例共用一只浏览器，
所以「当前页面」是全局状态；但「允许在哪些源上动手」按每次调用带的 `target` 取。
于是同一次会话里：`target=A`（只声明 8899）在 8900 页面上动手 → 拒；
`target=B`（声明了 8900）在**同一个页面**上动手 → 放行。这是对的——
调用方说「我现在是对 B 动手」，而那条声明正是为此存在的。反过来，**A 的声明不会因为 B 声明了 8900 而被放宽**。

**语义二：iframe 那一格是空的，因为够不着。** 这不是靠规则挡的，是 `document.querySelector`
的语义决定的：它只在顶层文档里找。所以「跨源 iframe 里的按钮被点，闸门核顶层源还是子框架源」
这个担忧不成立——那一格根本点不到。（工具面里没有「按坐标点击」，也就没有绕过去的办法：
§15.2 当初排除按坐标点击的那条理由在这里额外收了一次利息。）

#### 17.13.4 端到端冒烟搬进仓库（2026-10-02）

四轮验收里，**每一次抓到真缺陷的都是「把六个工具全跑一遍」这件事**，而它一直是一个躺在 `/tmp` 里的
一次性脚本——**跑不到 CI**。现在它是 `packages/devfront/test/tool-smoke.test.ts`：
13 条用例、真 Chrome、约 8 秒，门控在「本机有 Chrome」上（没装 Chrome 的环境跳过而不是红掉）。

**搬进来当天的第一条产出就是一条 kit 缺陷**：

```
Error: ENOTEMPTY: directory not empty, rmdir '…/T/dsh-cdp-<pid>-0'
 ❯ Function.launch packages/kit/src/chrome-cdp.ts:111
```

`Chrome.launch` 的默认 `userDataDir` 是 `dsh-cdp-<pid>-<port>`，而 `port` 缺省是 `0` ——
**同一个进程里起第二个 Chrome 会去 `rmSync` 掉第一个正在跑的 profile 目录**。
这条能在仓库里潜伏这么久，正因为此前**没有任何测试在一个进程里起过两个 Chrome**
（「另开一条 CDP 通路独立测量 `innerText.length`」那个用例恰好是第一个）。
修法：默认目录改用**进程内自增序号**，回归用例钉在 `packages/kit/test/kit.test.ts`。

**这条因果链值得记下来**：一个能抓到缺陷的探针，**只有进了常跑的门禁才算数**。
它躺在 `/tmp` 的四轮里抓到了四个 devfront 的缺陷，却一次都没机会碰到 kit——因为没人会想起来跑它。

#### 17.13.5 一次「更正」的更正：配置面**其实不存在**（2026-10-02）

这一小节记的是**我在同一个问题上偏了两次**，以及最后把它定下来的真机判据。

**第一轮（错因）**：我写「本 DSH 版本没有从 Config schema 自动生成设置页的机制」，依据是
「`suppressAutoSettingsPage` 在整份安装里搜不到」。那是**本仓 kit 自己的函数名**，DSH 那边的
入口叫 `settings.configure({ auto })`——**搜错字符串得出的反向结论**。

**第二轮（更正，也是错的）**：我据此改口，说「配置页是 DSH 自动生成的、而且它存在」，依据是
`dsh-settings` 的 `describe()`：

```js
const form = volatileForm(schema);  if (form === void 0) return []      // 没有 volatile 字段就不进表单
const autoGenerate = this.presentations.get(entry.fiber)?.auto ?? true  // 默认「开」
```

这段读得没错，**推理越界了**：我拿**生产侧**的代码当成**系统行为**，没有确认有没有渲染方。

**第三轮（真机，结论）**：profile 3082 + 真 Chrome，三个候选面全扫：

| 面 | 实测 |
|---|---|
| 插件详情页（`@hyzyn/dsh-devfront`） | 「包含的组件 共 1 个 · **1 运行中**」；`[data-plugin-config]` 不存在，控件 4 个（都是面板本身的）——**没有表单** |
| 设置 →「插件配置」 | 只有 **8 张**卡片，全部是**自带客户端半体**的插件；文本里不含 devfront |
| 设置 →「内置插件」 | 只读清单（`persona` / `tool-bash` … 29 个部署侧插件），与本包无关 |
| 全安装客户端代码 | **没有任何一处消费 `autoGenerate`**（`dsh-settings` / api-remotes / settings-controller 有它，UI 侧没有） |

**所以第一轮的结论碰巧是对的，第二轮的「更正」是错的**：宿主侧那套表单机制**在**，但**这一版
没有任何渲染方**——`autoGenerate` 有生产者、有传输层、**没有消费者**。

**那么 devfront 的 volatile 问题还算不算缺陷？算，但性质要降级说清：**

- 它违背的是**契约**：`.volatile()` 的含义是「可以热写、**不重挂插件**」，因此插件必须自己订阅
  `loader/volatile-update` 重读。docker / tty / codegraph 三个包都履行了，**只有它没履行**。
- 但它是**潜伏**的：触发它的写入方（`settings.update` RPC、配置编辑器）**在本版 GUI 里够不着**
  （没有配置面）。我**没有**找到一条「用户改了、界面说生效了、实际没生效」的可达路径——
  第二轮里我断言过那条路径，**那是我的推断，不是观察到的事实**。
- 修法不变（订阅 + 幂等重登记 + 三条边界），理由从「修一个用户可见的故障」改成
  「补上一处与其余三个包不一致的契约违背，并让它以后无论从哪条写入路径进来都正确」。
- 跨包守卫不变：`scripts/test/plugin-volatile-contract.test.ts`。

**更值钱的教训（这才是这一节该留下的东西）**：

1. **生产者存在 ≠ 有消费者。** 我两次都在读「机制的一半」就下全称结论：第一次搜错了名字，
   第二次读到了生产侧却没去找渲染方。判据应当是「**谁消费它**」，而不是「它有没有被算出来」。
   一个被算出来、被传输、**没人读**的标志，不是一个功能。
2. **静态事实与运行事实要分开标注。** 「`describe()` 会收录这类 entry」是**读源码**得到的
   宿主侧事实；「GUI 里有没有配置面」是**运行事实**。我第二轮把前者当后者用。
3. **bug 报告里最该写清的是「可达性」。** 同一个契约违背，可达（用户会撞）与潜伏（目前撞不到）
   是两种完全不同的严重度，也是我第二次偏掉的地方。

#### 17.4.2 Redis 通路 A **实现并真机验证**（2026-10-02）——第一个落地的引擎

**为什么是 Redis 先落地**：C2（账号）还没来，但 `248` 那台 Redis **无密码**、宿主**直连可达**，
而且 RESP 小到能自写——于是它成了**唯一现在就能真机验证**的引擎。其余仍卡在 C2 或防火墙。

**落地的东西（零依赖）**：

| 文件 | 是什么 |
|---|---|
| `src/resp.ts` | 极简 RESP 编解码 + **增量解析器**（分块、`null` bulk、嵌套数组、字节长度、缓冲上限） |
| `src/redis-executor.ts` | `ToolExecutor` 的 Redis 通路 A 实现：连 → （AUTH / SELECT）→ 发 → 整形 |
| `src/redis-command.ts` | 新增 `redisArgv()`：**命令切分的唯一实现**（内核与执行器共用，否则迟早漂） |

**三条刻意的设计**：① 执行器**不再解析命令**（内核已裁决，重解析就是第二个解析器）；
② 它**不写日志**（`AUTH` 的密码从这里流过）；③ 失败一律转 `{ok:false}`，
**把「Redis 没回话」说成成功比报错坏得多**。

**真机结果（`DEVDATA_REDIS_248=1 npx vitest run packages/devdata/test/redis-real-machine.test.ts`）**：

```
✓ ① 白名单读类放行且整形正确（PING→'PONG'、DBSIZE→number、INFO→string）
✓ ② SCAN 的嵌套数组整形正确（[游标, 键数组]）
✓ ③ 危险读 KEYS * / MONITOR 被拒（没给 dangerousReadCapability）
✓ ④ 被明确排除的 FLUSHALL / CONFIG SET / EVAL 进不来
✓ ⑤ 写 SET 被拒，且 EXISTS 反向核对 = 0（**那条写真的没发生**）
✓ ⑥ 审计记下了被拒绝的尝试
```

**第 ⑤ 条是这次的要点**：这台 Redis **没有 ACL**（4.0.14），「只读账号」那层**技术不可能存在**
——所以「只读」这句话**只**由代码层兑现。上面这条 `EXISTS = 0` 就是对它的**实证**，
不是对设计的复述。

**门控**：默认跳过（`DEVDATA_REDIS_248=1` 才跑），所以 CI 不需要能连到 `248`；
主机 / 端口可经 `DEVDATA_REDIS_HOST` / `DEVDATA_REDIS_PORT` 覆盖。

### 17.14 P3 落地：devdata 接成宿主插件（2026-10-02）

**这一步把「测试里跑得通」变成「宿主的真 ToolRuntime 收下了它」**。落地的东西与四条纪律记在
`packages/devdata/ROADMAP.md` 的记-11；这里只记**方案层面**的三件事。

#### ① 工具名带域前缀，因此「工具名」与「动作名」正式分成两件事

仓库守卫（`scripts/test/tool-names.test.ts`）要求 agent 工具名是 `<域>_<动作>`——工具名是**模型选工具
时唯一看到的标识**，撞族会让它在同族名字里误选（devfront 的 `web_*` 撞上宿主的 `web_search` 就是
这么发生的）。于是本包的工具是 `devdata_list_targets` / `devdata_redis_command` …，而矩阵里的动作名
保持引擎词汇（`list_targets` / `set` / `query`）。

**这不是改名，是把两个概念分开**，而 §17.12 的命令原文入口早就把它们分开了：Redis 上 agent 说的是
`devdata_redis_command`，而真正被裁决的动作是解析层从命令里算出来的（`set` / `keys` / `info`）。
所以 `TOOL_SPECS` 的每一项现在带 `name`（工具名）与 `action`（矩阵动作名）两个字段，
`preflight` 也吃 `entry`（可见性）与 `action`（裁决）两个参数。

#### ② 「可见面」收成「入口面」：没有执行器就不注册

`visibleTools` 回答「这个目标上允许做什么」（纯判定，不依赖宿主）；`entries.ts` 再叠一个条件：
**本机有没有这个引擎的执行器**。今天只有 Redis 有，所以 MySQL / SQL Server / 达梦 / RocketMQ 的目标
只注册引擎无关的三个自证工具。**注册一个跑起来必然失败的入口比不注册更坏**：agent 会先试、读一句
执行错误、再改，而正确的下一步根本不在那儿（本仓最忌讳的「配了没反应」）。

#### ③ 命令原文入口的代价现在付清了：写 / 危险读「不注册」在 Redis 上退化成「拒在判据层」

§3.6.1 的实现要求 ② 是「写 / 危险读默认不露入口」。它在 Redis 上**无法成立**——`GET` 与 `SET` 从
同一个入口进来，藏掉入口等于把只读也藏掉（§17.12 的必然结果）。所以那一档的可见面就是
`devdata_redis_command` **一条**，而闸门全部落在判据层：解析层先算出动作，再走可见性 → 裁决 →
能力 → 二次确认。**代价必须写在明处**：agent 看得到入口，撞墙时靠 `[CODE]` 与恢复路径找下一步。

#### 顺手修掉的三个真缺陷（详见 ROADMAP 记-12）

1. **RocketMQ 的受管动作在工具面上永远不可见**（`ENGINE_SPECIFIC` 手写清单与矩阵漂了）——
   补上反向断言（「每个受管**读**动作都该可见」）之后**当场就红**；
2. **`requiresConfirm` 只是回显**：共享环境里的不可逆操作**照跑**（第一次 `DEL` 就打出去了）。
   改成在 `preflight` 里拒（`CONFIRMATION_REQUIRED`），带 `confirmed: true` 才执行；
3. **注册清单走 `ctx.logger.info`**，真宿主启动日志里**什么都看不到**——仓库里这条教训
   （devfront 2026-10-01）已经记过一次。改用 `console.log`（docker / tty / devfront 同款）。
