### 记-2. CDP 驱动落地 + Chrome 客户端上收进 kit（2026-10-01）

| 落点 | 内容 | 门槛（已验） |
|---|---|---|
| `packages/kit/src/chrome-cdp.ts` | Chrome CDP 客户端（从仓根 `scripts/chrome-cdp.mjs` **上收**，零依赖） | 5 个既有消费者改从 kit 导入；仓根 `scripts/chrome-cdp.mjs` 只留**转发 shim**（实现只有一份） |
| `packages/kit/src/chrome-cdp.ts`｜`noSandbox` | 受限环境要显式关沙箱 | **不自动关**（关沙箱是安全相关默认值）；进程已死时**立刻**失败并给出可执行提示，不再等满 20 秒 |
| `src/cdp-driver.ts` | `CdpWebDriver` 实现 `WebDriver` 六个方法 | 真 Chrome 集成用例（`it.skipIf` 门控）12 条全过：导航 / 可见文本 / console / 真 PNG / 点击填值 / 换页清空 |

**上收的归属判据**：它原先住仓根 `scripts/`（L0），消费者已经跨两个包——根 `scripts/verify-*.mjs`、
`packages/docker/scripts/*`、本包的驱动。按「`kit` 是唯一的库」，跨包共用的实现该在 `kit`：
放在本包会让根脚本反向依赖一个私有包。

**实施中抓到的三个真问题**（都不是编译期能发现的）：

1. **仓根的 `scripts/` 根本无法 import `@hyzyn/dsh-kit`** —— 根清单的 `dependencies` 是
   *已发布*的插件版本，压根没有 kit。这正是原先那些脚本用 `../../../scripts/chrome-cdp.mjs`
   相对路径的原因。修法：把 kit 加进根清单的 `devDependencies`（它是 dev 期工具链）。

2. **`check-kit-pins` 的判据漏了 `devDependencies` 与仓根清单** —— 于是根清单那颗钉子
   **不受管辖**：可以钉着旧版本而闸门照样报绿。原判据的理由是「devDependencies 不进消费者的树」，
   那对*消费者的安装结果*成立，对*本仓这棵树*不成立——pnpm 的 `link-workspace-packages=true`
   只在范围匹配得上本地版本时才 link，否则**从 registry 拉一份**，也就是**同一棵树里两份 kit**，
   正是这道闸门要拦的事。已改为四字段全查 + 扫描仓根清单，并加了一条断言钉住「根清单在管辖内」。

3. **未捕获的异常不走 console API** —— 集成用例里那句 `setTimeout(() => { throw ... })`
   一开始完全收不到。`Runtime.consoleAPICalled` 只收 `console.error()` 一类；
   `setTimeout` / 事件处理器里 `throw` 走的是 **`Runtime.exceptionThrown`**。
   而「页面抛了未捕获异常」恰恰是「页面坏了」最常见、最该被验活抓到的信号——
   只订阅 console API 会把整类漏掉，且**漏得毫无症状**（报告里显示「console 干净」）。
   另外 `Log.entryAdded` 要单独订阅（资源 404 不走 console API），已一并接上。

**环境相关的实测发现**（写下来免得下次重新踩）：本机 Chrome **154** 起不来 CDP，
症状是「端点起来了约 1 秒后断开、命令全部超时」，而 Chrome 进程**还活着**。
stderr 里的真因是 `Failed to initialize sandbox` + `sandbox initialization failed: Operation not permitted`，
进程随后带 `SIGTRAP` 退出（GPU 子进程 exit 6）。加 `--no-sandbox` 后一切正常。
所以 `Chrome.launch` 现在会在进程已死时**立刻**失败并把这条提示写进错误里。

**由用例抓出的一处测试自身的错**：验「换页清空 console」时我让 `/other` 返回**同一个会抛错的页面**，
于是新页面又抛了同样的错——清没清都看不出来。改成返回一个真正干净的页面，并先断言「当前页确实收着那个错」
（否则断言可能因为压根没收到而假绿）。

### 记-4. 工具名 `web_*` → `site_*`（2026-10-01）

**触发**：有人问「`web_open` 这个工具名会不会有歧义」——会，而且是**实打实的撞族**。

宿主自带 `@deepseek-ai/dsh-tool-web`，它定义了 **`web_search` / `web_fetch`**。原先那六个工具
（照 plan §15.2 抄的 `web_*`，而 §15.2 写的时候还没和宿主的 `web_*` 对上）会与它们并排出现在
同一份工具清单里：**同前缀，域完全不同**——

| | 宿主 `web_fetch` | 本包 `web_open` |
|---|---|---|
| 取什么 | 公网 URL 的 HTTP 响应 | **内网站点的浏览器页面** |
| 机制 | HTTP 客户端（**不跑 JS**） | headless Chrome |
| 边界 | 公网 | `scopeDirs` + 站点白名单 |

危险不是「看起来像」，而是一条具体的误选路径：**SPA 用 `web_fetch` 拉回来是个空壳**（JS 没执行），
模型据此判断「页面坏了」——正是本插件要消灭的**假阴性**。`web_text` 与 `web_fetch` 在语感上
更是同义词。

第二重歧义：本仓 `web` 还指 **Web GUI**（`webServer` 服务、web profile），而 GUI 自己的插件 id
是 `ui-*`——所以 `ui_*` 也不能用。

**改法**：`site_open` / `site_shot` / `site_click` / `site_fill` / `site_text` / `site_console`。
选 `site_` 的理由是它与**配置词汇**一致（`targets[]` = 站点、`WebTarget` = 站点），一个词贯穿
配置与工具名；且不与 `web_*`（宿主公网）、`ui_*`（GUI）、`docker_*`、`tty_*`、`sftp_*` 撞族。

**为什么现在改最便宜**：这六个名字还没装进任何 profile、没有 agent 学过它们。
装进 test profile 之后再改就是破坏性的了。

### 记-5. 工具命名规则 + 守卫（2026-10-01）

`docs/conventions.md § 命名` 那张表原先**没有 agent 工具名这一行**（有包名、插件 id、配置命名空间、
HTTP 路由、环境变量、缺陷编号，唯独没有工具名）。所以 `web_*` 那个撞族没有任何东西拦得住。

补齐两件：

1. **规则写进 `conventions.md`**：`<域>_<动作>`，域 = 该工具**操作的对象或能力**（不是包名）；
   **不得占用宿主已用的域前缀**（当前保留 `web_` / `ui_`）。
2. **守卫 `scripts/test/tool-names.test.ts`（7 例）**：扫全仓 `defineTool` 的工具名，判三条——
   不得用保留前缀、前缀必须是**登记过的域**、名字形状。

**守卫立刻找出一处既有漂移**：`tunnel_list` 在 `tty` 包里但用的是第三个前缀（`tunnel_`，
不是 `tty_`）。这不是错，是「同包不同域」——所以登记表里补上了它，并写明域是**端口转发隧道**
而不是终端会话。这条恰好说明守卫的用处：它把「同包不同域」从**默认允许的偶然**变成
**必须显式登记的有意**。

**实施中的一个真 gotcha**：JSDoc 里写了 glob `packages/*/src/*.ts`，而其中的 `*/`
**提前闭合了块注释**，后面的字符变成代码 → `ReferenceError: src is not defined`。
注释里出现 `*/`（glob、正则、路径都容易带出来）就是这个后果，改写掉即可。

### 记-6. 上收 `scope.ts` 进 kit + devfront 改回插件打包（2026-10-01）

**触发**：准备装进 test profile 时发现**装不上也跑不起来**，两个拦路问题都不是编译期能发现的。

| 拦路问题 | 证据 | 修法 |
|---|---|---|
| ① 入口指向 `src/index.ts` 且**没有 build** | 纯 Node 加载报 `Cannot find module .../src/console.js`（源码用 `rewriteRelativeImportExtensions`，`.js` 指向的编译产物不存在）。而**每一个已挂载的插件**都是 `main: lib/index.js` + `build` 脚本 | 加回 `build: tsc -p tsconfig.json`，`main`/`types`/`exports` 指向 `lib/` |
| ② 运行时依赖 `@hyzyn/dsh-devdata: workspace:*` | profile 不是 pnpm workspace 成员，`workspace:*` 在 profile 里报 `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND`（这正是 `check-publishable` 存在的理由）。而且就算解析得了，devdata 也没有 build，`devfront` 编译后的 `lib/*.js` 会去 import 一个 `.ts` | **把作用域门 `scope.ts` 上收进 `kit`**（唯一有构建产物的共享库），devfront 改从 `@hyzyn/dsh-kit` 导入，`devdata` 那个子路径导出退成转发 |

**为什么这次上收是必然的**（原先记 E10 时的触发条件是「`devenv` 也要用时再说」）：
真正的触发条件比那更硬——**运行时加载**。插件挂进 profile 后由宿主用纯 Node 加载，
跨包 import 另一个私有插件的 `src/*.ts` 走不通；把它做成运行时依赖又被 `workspace:*` 拦住。
所以「作用域门该在 `kit`」不是整洁度问题，是**能不能装上**的问题。

**由此得到的一条判据**（值得记住）：**「库」与「插件」的打包形态不同**。
`devdata` / `devfront` 起初按「库」做（无 build、入口指 `src/*.ts`，因为只被 vitest / tsc 消费）——
这在它们**不是插件**时是对的（当时还专门为它去掉了 `build`，见 `devdata` 记-4）。
但 `devfront` 一旦成为插件，就必须回到「插件」形态：**宿主用纯 Node 加载它**。
`devdata` 仍然不是插件（它没有 `dsh.bundle.patch`），所以它保持「库」形态不变。

**验收**：纯 Node 能 `import` 编译产物，且 `name` / `inject` / `apply` 三个导出都在；
`pnpm -r build` 产出 `packages/devfront/lib/`；全仓 2077 测试与五项守卫全绿。

### 记-7. 真机冒烟抓到的 favicon 噪声规则 bug（2026-10-01）

**怎么抓到的**：不是靠单测——单测全绿。是写了个**端到端冒烟**（假宿主 ctx + 真 Chrome + 本地夹具页），
让插件**自己注册的工具**跑一遍并打印 agent 会看到的东西。第一次跑出来：

```
console 共 3 条：本站错误 2、告警 1、噪声（已排除）0
  ✘ Failed to load resource: ... 404 (Not Found)（http://127.0.0.1:61912/favicon.ico）
  ✘ Error: 未捕获：渲染订单行失败
```

**第一个「本站错误」是 favicon 404** ——它本该是噪声。也就是说**「噪声淹掉信号」这件事本身发生了**：
一次干净的页面上，报告的第一条永远是浏览器自动请求的 favicon。

**两处真 bug**：

1. `console.ts` 的 `favicon-404` 规则要求**正文**含 `favicon`，而 CDP 给的正文是
   `Failed to load resource: the server responded with a status of 404 (Not Found)`——
   **里面没有 favicon**，那个名字只在 `sourceUrl` 里。所以规则在真机上**从不命中**。
   判据改为看 `text + sourceUrl`。
2. 驱动**从来没有填 `status`**：CDP 的 `Log.entryAdded` 没有状态码字段，状态码写在正文里。
   于是按状态分档的规则全部静默失效。新增 `extractStatus()` 从正文取回来（取不到返回 `undefined`，
   **不猜**——给错状态码会让规则反向生效）。

**为什么单测没抓到（值得记住的一条）**：我原来的 fixture 是
`'Failed to load resource: favicon.ico'` + `status: 404`——**把 favicon 写进了正文、还手动给了状态码**。
也就是说 fixture 比现实"友好"，它验证的是**我想象的 payload**，不是 CDP 真正发的那个。
正因如此新用例改成逐字照抄 CDP 的真实措辞，并补了一条反向用例：
**不带 favicon 的资源 404 不算噪声**（守住"别放宽成任何 404 都是噪声"——那会吞掉一整类真故障）。

**由此得到的一条判据**：**「能跑」与「跑得对」之间的差距，只有真跑一遍才显形**。
这一层的输入来自一个外部协议（CDP），fixture 的作者很容易把它写成自己以为的样子。

### 记-11. 第二轮验收：两个**同类**漏网 + 两条边界（2026-10-02）

记-10 修完四条后复验（15 次调用）**全部通过**。但验收方列了「有几个数我拿不到 / 没法核对」——
一查，其中两条是**同一个缺陷类的镜像版**，正是记-10 那四条的病根：

| # | 缺陷 | 修法 |
|---|---|---|
| 5 | `site_text` 的 `truncated`/`length` 声明在 schema 里，渲染层只在截断时才写 → agent **永远拿不到**，且「没截断」变成靠缺席表达的信号 | 渲染末尾**始终**附 `—— 全文 N 字符（未截断）` / `—— 已截断：本次返回前 N 字符，全文 M 字符` |
| 6 | `site_console` 只给噪声**计数**、不展开构成 → 被排除的东西**不可核对**，规则误伤真错误也没人看得见 | 输出加 `noiseRules`（`favicon-404 ×1`），渲染加「噪声构成：…」；信息类日志补规则名 `page-log` |

**教训（比缺陷值钱）**：修完一类缺陷要**回头找它的镜像**。「声明的契约」与「实际交付给 agent 的东西」
是两端——记-10 只查了「产出 ≠ 声明」（`clicked` vs `selector`），没查「声明了 ≠ 交付了」。
守卫因此扩了：渲染层始终可见 + 噪声构成可核对。

**同轮补验的三件事**：
- `site_fill` **`input` 与 `change` 都派发**（专门做了一页只监听事件名的夹具实测）；
- 「全文 4468 字符」有独立来源：另开一条 CDP 通路读 `innerText.length`，独立测得 **4468** 一致；
- **噪声计数在同一会话里不稳定**：首次 2 条、再次 1 条（Chrome 缓存了 favicon 的 404）。
  → **`噪声数 == N` 不能当断言写**；能断的是 `本站错误 == 0` 与 `noiseRules` 里出现预期规则。

**两条边界（记录，不是缺陷）**：
- `open` 的闸门**只管打开的那个 URL**，管不了页面自己往哪跳：夹具里一页 `location.replace()` 到
  另一个源（`open` 时合法），跳完之后 `site_text` 读到的是**异源页**的内容。
  设计使然（登录跳转必须允许），但它划定了保证范围：**审入口，不审页面的自我导航**。
- **iframe 内容读不到**：`innerText` 不含子文档 → 跨源 iframe 的文字进不了 `site_text`。
  这一侧是**结构性排除**的，不靠规则挡。

### 记-12. ★ 跨源动作闸门：读放行，动手不放行（2026-10-02）

**这条是验收方找出来的，不是我。** 它在核记-11 那条「`open` 的闸门管不了页面自己跳去哪」时发现：
实际放行的**不只是读**。两个探测的证据链：

```
① site_open http://127.0.0.1:8900/   → [SITE_NOT_ALLOWED]   ← 入口拦死
② site_open .../redirect.html（合法）→ 页面自己跳到 8900
   site_text → FOREIGN ORIGIN PAGE                          ← 读放行（设计使然）
③ site_click body → 已点击 body                            ← **写也放行，没有任何拒绝**
```

它的判词：「读异源内容我是当作**不受信的输入数据**处理的；但对异源页**动手**是另一回事。
『审查入口』变成了『审查入口，除非页面自己把你带出去』。」

**判断成立，而且不是「文档没写清」——是漏了一道闸门**：origin 判据写在 `if (action === 'open')`
里面，其余动作压根没有 origin 判据。修复前实测 `site_click` 与 `site_fill` 在异源页上都会成功，
**异源页真的被改动了**（`fill` 那条验收方只测了 `click`，并明说「按同一通路推断，但那是推断不是证据」；
补测结论：同样放行）。

**修法**（按验收方建议，唯一一处它接受的做法）：

| 面向 | 处理 |
|---|---|
| `open` | 不变：入口同源 + 声明路径前缀内 |
| `text` / `shot` / `console`（读） | **放行**——登录跳转后读页面、截图是登录流程的必要部分 |
| `click` / `fill`（动手） | **执行前核「当前页面」的源**，不在允许集合内一律拒（`PAGE_ORIGIN_NOT_ALLOWED`） |

**三个实现要点，每个都有用例钉住**：

1. **必须实时问浏览器，不能在纯判定层静态判。** `adjudicateWebAction` 看不到浏览器；
   而驱动自己记的 `lastUrl` 是「上次导航到哪」，**客户端跳转不会更新它**——那恰好是这道判据要防的东西。
   所以 `WebDriver` 新增 `currentUrl()` 这条**事实**接口，由判定层决定拿它做什么（层次不能倒）。
2. **源要显式声明才放行。** 新增 `WebTarget.allowedOrigins`（缺省 `[]` = 只能在**声明源上动手**）。
   需要它的理由：登录 / SSO 跳到 IdP，**填账号密码就是在那个源上动手**，只允许声明源会把登录整条掐掉。
   但代价不能由规则偷偷承担——**页面自己跳过去不构成授权**。
3. **读不到当前页面源 = 拒绝**（fail-closed）；配置里解析不出来的 origin 条目**不授予权限**。

**端到端复验**（同夹具、真 Chrome）：异源页上 `click`/`fill` 都返回 `[PAGE_ORIGIN_NOT_ALLOWED]`，
**异源页没被改动**；读仍放行；同源上的点击与填值不受影响。

**给下一个人**：这条边界现在的准确表述是「**读可以跨源，动手不可以，除非显式声明那个源**」。
记-11 里那句「审入口，不审页面的自我导航」**不够准**——它读起来像只漏了信息，实际当时漏的是写。

### 记-13. 把跨源闸门问到边：五条补测全过 + 两条语义（2026-10-02）

收紧之后验收方列了五条「相关但没验证」。第一条提法是**对的**：它说那条恢复路径
「我没真去改配置再回验，所以『走得通』只是**读到的文字**」——一条走不通的恢复路径比没有还坏。
五条一次测完（完整记录在 [方案 §17.13.3-1](../../docs/devdata-plan.md)）：

| # | 追问 | 结论 |
|---|---|---|
| ① | `allowedOrigins` 恢复路径真走得通吗 | **走得通，且动作真落到页面上**（异源页放只监听 `input` 的哨兵，填完被触发）。不是「放行但没做事」 |
| ② | `site_shot` 在异源页也放行吗 | **放行**（真 PNG）——此前只有推断 |
| ③ | 多 target 会互相影响吗 | **不会**：同页面同浏览器，换个 target 判决就变 |
| ④ | 二次导航有无残留 | **无**：回本站恢复放行；再跳异源又被拒 |
| ⑤ | iframe 内元素被点算哪个源 | **问题不存在**：`querySelector` 不下钻子文档 → 结构性不可达；点 `iframe` 元素本身判**顶层源** |

**语义一：授权按「调用里的 target」查，页面状态是全局的。** 一个插件实例共用一只浏览器，
「当前页面」是全局的；但「允许在哪些源上动手」按每次调用的 `target` 取。
`target=A`（只声明 8899）在 8900 页面上动手 → 拒；`target=B`（声明了 8900）在**同一页面**上动手 → 放行。
这是对的——调用方在说「我现在是对 B 动手」。反向也验了：**A 的声明不因 B 声明了 8900 而被放宽**。

**语义二：iframe 那一格是空的，因为够不着。** 不是靠规则挡的，是 `document.querySelector`
的语义决定的——它只在顶层文档里找。§15.2 当初排除「按坐标点击」的那条理由
（「那没有可复审的选择依据」）在这里额外收了一次利息：**没有坐标点击，也就没有绕进子框架的办法**。

### 记-14. 端到端冒烟搬进仓库（`test/tool-smoke.test.ts`）——当天就抓到一条 kit 缺陷（2026-10-02）

**搬到哪、怎么跑**：`test/tool-smoke.test.ts`，**13 条用例、真 Chrome、约 8 秒**，
门控在 `describe.skipIf(!CAN_DRIVE_CHROME)`（没装 Chrome 的环境**跳过而不是红掉**，与
`cdp-driver.test.ts` / `packages/tty/test/stats.test.ts` 的 `CAN_PROBE_*` 同口径）。

**为什么搬**（这四轮它抓到过：`click`/`fill` 的输出契约、异源页上动手放行、`truncated`/`length`
交付不到、噪声不可核对）：它的价值不在「覆盖得多全」，而在**它是唯一一个会把整条链路真的跑起来的东西**。
而它此前躺在 `/tmp` 里——**跑不到 CI**。

**搬进来当天就证明了这句话**：它立刻打出一条 kit 的缺陷——

```
Error: ENOTEMPTY: directory not empty, rmdir '…/T/dsh-cdp-<pid>-0'
 ❯ Function.launch packages/kit/src/chrome-cdp.ts:111
```

`Chrome.launch` 的默认 `userDataDir` 是 `dsh-cdp-<pid>-<port>`，而 `port` 缺省是 `0`：
**同一个进程里起第二个 Chrome 会去 `rmSync` 掉第一个正在跑的 profile 目录**。
这条能在仓库里潜伏这么久，正因为此前**没有任何测试在一个进程里起过两个 Chrome**
（我那个「另开一条 CDP 通路独立测量 `innerText.length`」的用例恰好是第一个）。
修法：默认目录改用**进程内自增序号**（`defaultUserDataDir()` 导出以便单测），
回归用例钉在 `packages/kit/test/kit.test.ts`。→ 记在 `kit D14`（编号需维护者点头）。

**三个设计选择**：

1. **是 vitest 测试，不是独立脚本**——这样它进 `pnpm test`、受全仓门禁管，
   且失败会指名到具体用例（而不是一整段 `console.log`）。
2. **夹具用代码内 HTML + 两个临时端口**（站点 + 一个真正的异源），不起外部依赖、不引入 fixture 文件。
   异源那个端口是**全部跨源判据的实验台**：`localhost` 与 `127.0.0.1` 也能算异源，但用**端口不同**
   更不容易被 DNS / hosts 之类的环境因素干扰。
3. **每个用例自己导航**，不依赖前一条留下的页面状态——冒烟一旦依赖执行顺序，
   失败信息就会变成「前面那条挂了」而不是「这一条挂了」。

**仍未覆盖的**（写在最前面免得误以为它很全）：页面内 `fetch` 跨源、DNS rebinding、批量穷举，
以及 `allowedOrigins` 在**真实 SSO 流程**里的表现（只验过夹具上的允许/拒绝与「真的能动手」）。

**搬进来之后的第一个副作用（如实记）**：第一版里有条用例为了拿「全文多少字符」的**独立真值**，
另开了一朵 Chrome 问 `innerText.length`。那多出来的一个浏览器进程把整套测试的负载抬高，
足以踩红 `tty probe.test.ts` 里那条**自述「负载下间歇红」**的用例（tty D95）——
全仓出现约 **1/3 的间歇红**，而它在这次改动之前 6 次连跑全绿。**这是这次搬家的真实代价。**

修法不是去掉那个独立判据，而是换个更省的做法：**让页面自己算**——
首行放一个与结果**等宽**（各 6 字符）的占位符，页面把 `document.body.innerText.length` 写进去，
写完长度不变，于是它就是浏览器算出来的真值，**与我的截断/记账逻辑完全无关**，
而且不起第二个进程（那条用例 1515ms → 324ms）。

**改后实测**：全仓连跑 **10 次，9 次全绿**，1 次红——那 1 次是**紧接全量 `build` + `typecheck`
之后立刻跑测试**（机器还在忙），不是常规跑法。两次观察到的红都落在**别的包**的
负载敏感用例上（tty D95 的 `probe`、codegraph CG65 的「启动争抢」），**没有一次是我的用例**。

**残留的不确定性要说清（2026-10-02 晚些时候补，含一条自我更正）**：上面说「真正的修法是让那两条
用例的有界等待不那么脆」——那是**推测，不是证据**，现已撤回。我去复现它们，四个场景全绿：

| 场景 | 结果 |
|---|---|
| `packages/tty/test/probe.test.ts` 单文件连跑 | **8/8 绿** |
| 同上，外加 12 个饱和 CPU 的 busy loop（10 核） | **8/8 绿** |
| 整个 `packages/tty`（42 文件，531 条）连跑 | **3/3 绿** |
| **全仓**（127 文件，2127 条）连跑 | **3/3 绿**（2126 passed / 1 skipped） |

**所以我不能声称那两条用例「固有脆弱」**——只能说：观察到的那两次红，都发生在**另开一朵 Chrome

断言，就是用推测去换真实代码）。若它们以后在 CI 上继续偶发，届时再按那时的证据处理。

### 记-15. volatile 契约的义务补上了；配置面**不存在**（一个问题上偏了两次，真机定案）（2026-10-02）

这一条记两件事：**补上的是契约义务**，以及**我在「有没有配置面」上错了两次**。

#### ① 补的是什么：一处潜伏的契约违背

`Config` 的字段全标 `.volatile()`，而它的含义是「**可以热写、且不重挂插件**」——loader 检出
「只变了 volatile 字段」后只把配置引用**就地改写**、发 `loader/volatile-update`，插件**不会**
被重新 `apply`。所以这个声明的配对义务是：**插件自己订阅那个事件并重读**。

仓库里三个包都履行了，只有本包漏了：

| 包 | 订阅 |
|---|---|
| docker | `src/index.ts:3707` `scope.onChanged(() => applySection(scope.get()))` |
| tty | `src/index.ts:5030` `scope.onChanged(() => applyPatch(scope.get()))` |
| codegraph | `src/index.ts:4058` `scope.onChanged(() => sync(scope.get()))` |
| **devfront** | 本轮补上 |

**性质要说准**：这是**契约违背**（与其余三个包不一致），但它是**潜伏**的——见 ②，触发它的写入方
在这版 GUI 里够不着。我一度把它写成「用户改了配置、界面说生效了、实际没生效」，**那是我从宿主侧
源码推出来的路径，不是观察到的事实**。

修法照既有写法：`live` 由 `const` 改 `let`；抽出幂等的 `refreshTools()` / `refreshAnnouncement()`
与 `applySection(raw)`——重算 → 拆上一轮 → 重建浏览器（`settleMs`/`noSandbox`/`chromePath`/
`shotDir` 只在构造时读一次）→ 重新登记。工具**执行体**在调用时读 `live`，只有**描述里嵌了站点
名单**的那些必须重新注册。

顺带钉住三条边界（各有用例）：**空对象不当配置**（`describe` 未就绪时的 `{}` 会把六个工具整批
抹掉）、**值没变的广播不拆装**（`loader/volatile-update` 是全仓广播，kit 的 `onChanged` 不按
entry 过滤）、**没有 settings 服务的宿主照旧可用**。

**验证**：`test/volatile-config.test.ts` 9 条，走真实写入顺序（先落盘再广播）；并做变异验证——
把订阅回调里的重读去掉 → **5 条红 / 4 条绿**，绿的正是那些刻意不依赖重读的（启动时 resolved 优先、
空对象守卫、无变化广播、无 settings 宿主），与设计相符。

**真机确认（本轮新拿到）**：profile 3082 的插件详情页显示 **「包含的组件 共 1 个 · 1 运行中」**
——新 `lib/` 挂载成功，上面这轮重构没有把插件搞崩。

#### ② 更正过两次的那件事：GUI 里**没有**配置面

| 轮次 | 我说过的话 | 依据 | 判定 |
|---|---|---|---|
| 1 | 「本版本没有从 Config schema 自动生成设置页的机制」 | 拿**本仓 kit 自己的** `suppressAutoSettingsPage` 去搜安装——**搜错了字符串**（DSH 的入口叫 `settings.configure({ auto })`） | 结论**碰巧对**，依据错 |
| 2 | 「配置页是 DSH 自动生成的、而且它存在；volatile 是配置页存在的前提」 | `dsh-settings` 的 `describe()` 按 `volatileForm(schema)` 收录、`autoGenerate` 默认 `true` | **错**：读的是**生产侧**，没找**渲染方** |
| 3 | **「GUI 里没有配置面」** | 真机三面扫描 + 全安装 grep | **定案** |

第 3 轮的判据（profile 3082 + 真 Chrome）：

| 面 | 实测 |
|---|---|
| 插件详情页 `@hyzyn/dsh-devfront` | 「包含的组件 共 1 个 · 1 **运行中**」；`[data-plugin-config]` **不存在**，控件 4 个（面板自身的）——**没有表单** |
| 设置 →「插件配置」 | 只有 **8 张**卡片，全部是**自带客户端半体**的插件；整页文本不含 `devfront` |
| 设置 →「内置插件」 | 只读清单（`persona` / `tool-bash` … 29 个部署侧插件），与本包无关 |
| 全安装客户端代码 | **没有任何一处消费 `autoGenerate`**（生产在 `dsh-settings`，传输在 api-remotes / settings-controller，UI 侧无） |

所以宿主侧那套表单机制**在**（`describe()` 会收录这类 entry、`update()` 会因缺 volatile 字段而抛
`has no volatile fields`），但**这一版 Web GUI 里没有渲染方**——`autoGenerate` 有生产者、有传输层、
**没有消费者**。

**字段为什么仍保持 `.volatile()`**：与 GUI 无关。它是 `settings.update` RPC 与配置编辑器那条
**无重挂**写入路径的前提，而本包现在履行了订阅义务。要不要补客户端半体（像 docker 那样自带卡片）
仍是纯增量，默认不补。

#### ③ 教训（比结论值钱）

1. **生产者存在 ≠ 有消费者。** 两次偏差都是「读机制的一半就下全称结论」：第一次搜错了名字，
   第二次读到了生产侧却没去找渲染方。判据应当是「**谁消费它**」，不是「它有没有被算出来」。
   一个被算出来、被传输、**没人读**的标志，不是一个功能。
2. **静态事实与运行事实要分开标注。** 「`describe()` 会收录这类 entry」是**读源码**得到的宿主侧
   事实；「GUI 里有没有配置面」是**运行事实**。第 2 轮我把前者当后者用。
3. **同一处连错两次，说明我的判据里缺了「谁消费」这一环，而不是缺了一次核对。** 所以这次补的是
   **跨包守卫**（`scripts/test/plugin-volatile-contract.test.ts`：有 volatile 字段的包，源码里必须
   出现订阅；只在注释里提一句不算）＋ L0 的一节判据（`docs/conventions.md § 插件配置`），
   而不是再多读一遍源码。

### 记-16. 第一次指向**真站点**（卫健委 hcckc 测试环境）：两个真值坑（2026-10-02）

所以没有改 profile，而是用**插件自己的宿主半体**（`packages/devfront/lib` 的 `apply`）+

#### 跑出来的结果

| 工具 | 结果 |
|---|---|
| `site_open` | 允许，6629ms，打开了真页面 |

#### 两个真值坑（夹具碰不到的）

**① `site_text` 的假阴性：关键文案可能**烤在图片里**。**

截图里有「2026年 上海市卫生健康行业网络安全知识竞赛」和「承办单位：上海市卫生健康委员会」，
而 `site_text` 给的是另一套（`承办单位：\n上海市健康数据产业协会`）。查证链条：

| 假设 | 实测 |
|---|---|
| 页面在过渡、读早了 | **否**：按 500ms 采样 40 次，从 **762ms 起 20 秒内一个字都没变** |
| 文字在 DOM 里只是 `innerText` 没给 | **否**：`innerHTML` / `textContent` / 全部 CSS（含伪元素 `content`）/ SVG text / shadow DOM / canvas **都没有「竞赛」这个字符串** |
| 截图拍错了页 | **否**：截图跟随页面（空白页 / 本站 / example.com 三个哈希各异，同页两次一致）；`/json/list` 只有一个 page target（`#/login`） |
| **在伪元素的 `background-image` 里** | **是**：`div.login::before` → `url(static/jpg/background-cb1d3ffb.jpg)`，**1425×757 的整屏 JPEG**，标题和「承办单位」水印都烤在里面 |

会**报失败，而人眼看得见**。**结构性假阴性**。

修法（已做）：把「取不到什么」写进 **工具描述 + 能力公告**——图片里的字（含伪元素
`background-image`）、canvas、SVG 文本、closed shadow DOM、iframe 内内容，并给出复核动作：
**「应包含某段文字」失败时先 `site_shot` 看一眼**。之所以不做成「自动检测有没有大背景图」：
那是替 agent 猜，而它有能力自己看图。

**② 空标题被渲染成一对空括号。**

`site_open` 当时输出 `已打开 https://…（标题：）`——数据是对的（那个 SPA 的 `document.title`

这与记-11 那两条是同一个病根的另一面：**负信号不能靠一个看着坏掉的形态来表达**。

### 记-17. 移动端 H5 没有移动视口：能力在驱动里，却接不出来（2026-10-02）

**怎么发现的**：记-16 那次真站点登录跑通后看登录后的截图，发现**页面被放大成桌面宽度**——
而 `hcckc-h5` 是**移动端 H5**。顺着查驱动：

```
cdp-driver.ts   viewport?: { width; height }            ← 接口有
cdp-driver.ts   Emulation.setDeviceMetricsOverride(...) ← 实现了
grep 全仓       传 viewport 的地方：0 处                 ← 零调用方
plugin.ts       构造驱动只传 settleMs / noSandbox / chromePath / shotDir
Config         没有 viewport 字段
```

**能力在驱动里，插件层接不出来**，于是六个工具**永远用默认桌面视口**（实测 1440×757）。
而本机要验的前端里 `hcckc-h5` / `bpaimsm-v4` / `bpaossm-v3.1` **都是移动端 H5**。

**一个副产品（比缺陷本身更值钱）**：记-16 里我把「截图里两层内容叠在一起」记成了**站点**的现象。
**那是本工具视口错误的产物**——桌面视口下整屏背景图被缩放/裁切，图里烤着的「主办单位」等文字
落到了表单上；手机视口下同一页面版式是干净的（见两张截图的对照）。
**工具自己的缺陷伪装成了被验对象的缺陷**——这是最难查的一类，因为你会跑去查页面。

**为什么夹具不可能暴露它**：夹具是我写的，我用桌面视口看它，它就在桌面视口下是对的。

**修法**（按站点配视口）：

| 位置 | 改动 |
|---|---|
| `page.ts` | `WebTarget.viewport?: { width; height }` |
| `plugin.ts` | `TARGET_SCHEMA.viewport`（串 `"390x844"`，默认空）+ `parseViewport`（**不猜**：写坏了当作没写，宁可浏览器默认，也不在一个没人选过的窗口里验活） |
| `cdp-driver.ts` | 新增 `ensurePage(target)`：**按动作随 target 施加**视口——一个浏览器服务多个站点，所以不能只在起浏览器时定死；换回没写视口的站点时 `clearDeviceMetricsOverride`（**撤销**，不是留着上一个站点的）。值没变不发 CDP |
| `CdpWebDriverOptions.viewport` | 从「唯一的视口」降级为**默认视口**（站点没写时用它）——原先它零调用方，现在有了明确的语义 |

**证据**：

- 真机同一个页面、同一朵浏览器内来回切：`target=phone` → **390×844**，`target=desktop` → **1440×757**；
- `test/cdp-driver.test.ts` 的集成用例断言**两向**：手机 target 拿到 390×844，换回默认 target 时
  宽高**不再是** 390/844（撤销真的发生了，而不是碰巧没生效）；
- `test/plugin.test.ts` 钉住 `parseViewport` 的收/拒边界（含 `0x0` / `5x5` / `10.5x20` / 非字符串）。

**仍然没验到（要说清）**：这**不是真设备模拟**——`mobile: false`、`deviceScaleFactor: 1` 仍是写死的，
touch 事件、DPR 2/3 下的图片清晰度、移动 UA 分支**依然验不了**。那要另做一层（UA / touch / DPR），
本轮刻意不扩。

### 记-18. 双读审计噪声模型：它没误报，但**有两条规则永远不会命中**（2026-10-02）

**为什么单做这一件**：噪声模型是这套工具里**唯一从未接触真实输入**的部件——五条规则全是我照着
**自己写的夹具**总结的。夹具能验「规则按我写的那样工作」，**发现不了我不知道的噪声**。

#### 方法：单浏览器、单会话的**双读**

同一朵浏览器、同一个 driver 实例里读两遍：

| 读法 | 拿到什么 |
|---|---|
| `driver.console({ target })` | **原始消息**（`level` / `text` / `sourceUrl`，不分档） |
| `invokeWebAction({ request: { action: 'console' }, driver })` | **三档分类**（本站错误 / 告警 / 噪声 + 规则名） |

**为什么必须同源同会话**：一边用工具、一边另起浏览器抓，两边的消息集合可能不同（缓存、时序、
失败的第三方请求次数），差异就分不清是「分类错了」还是「两次加载不一样」。同一个 driver 里，
这两个视图在实现上就是**同一批消息**。

#### 页面与作用域（都由证据定，不猜）

- 页面：`http://dev.example.com:82/bpaoss_njtj/login/`（特种设备 bpaoss 测试前端，UmiJS SPA）；
- `scopeDirs` = `webproject/ClientOSS/bpaoss-web-v2.1`——判据是那个**确切 URL 只出现在它的
  `config/`**（`config.njtjossTest.js` / `config.njntossTest.js`）。线上 `umi.6b515dfc.js` 与本地
  dist 的 `umi.76adcf36.js` 不一致，说明线上是**更早**的构建；这不影响噪声审计。

#### 结果：原始 2 条，分类全对，**假警报方向被正确挡住**

| 原始消息 | 来源 | 落档 |
|---|---|---|
| `[debug] Config loaded` | `umi.6b515dfc.js`（本站） | 噪声 · `page-log` |
| `[error] Failed to load resource: 404` | `…:82/favicon.ico`（**同源**） | 噪声 · `favicon-404` |

第二条是关键：它是**同源** 404，按「本站资源」主判据会算成「本站错误」——而缺个 favicon 不是
页面坏了。**这正是最危险的方向（假警报）**，它在真机上被正确挡住了。

**假阴性方向本来就有守卫**（`console.test.ts` 的「不带 favicon 的资源 404 不算噪声」与「本站的
未捕获异常不会被 favicon 规则误吞」），本次又把**真实样本**补了进去。

#### 真发现：两条噪声规则**永远不会命中**

`Chrome.launch` 默认起的是**全新临时 profile**（`dsh-cdp-<pid>-<seq>`，dispose 时删掉）——
**没有任何扩展**。而：

| 规则 | 可达条件 | 结论 |
|---|---|---|
| `favicon-404` / `page-log` / `resizeobserver-loop` | 与扩展无关 | ✅ 可达（前两条本次真的命中了） |
| **`extension-inject`** | 来源是 `chrome-extension://` | ❌ 装不了扩展 → **永不命中** |
| **`third-party-blocked`** | `ERR_BLOCKED_BY_CLIENT`（**广告拦截扩展产生的码**） | ❌ 同上 |
| `browser-internal` | 来源是 devtools / about: | ⚠️ 近乎不可达 |

而**公告**（`DEVFONT_GUIDANCE`）把它们说成已覆盖——**声明了却永远拿不到**，正是这套东西自己
立的那条规矩。修法（已做）：把**可达性**写进公告 + 两条规则的注释 + 两条守卫
（公告必须写明；`ERR_NAME_NOT_RESOLVED` 这类第三方不可达**必须仍是告警**，不许为了「让规则命中」
把它放宽成「凡是第三方域名都算噪声」——那会把真实的第三方故障一起吞掉）。

#### 仍然没验到（这条比上面都重要）

**没有一条真实的本站错误落进 `error` 档**——两个页面（`hcckc-h5` 登录页/登录后、bpaoss 登录页）
都是 0 条。所以**「`本站错误 0` 作为通过判据」这条最关键的路径，至今没有被真实输入检验过**：
真错误会不会被某条规则误吞、来源判据在真实故障上对不对，都还只有夹具与合成样本支持。
要检验它，需要一个**真的出错**的页面（发布出问题的那种）。

**顺带**：`chrome-extensions` 那两条规则要变成「条件可达」，得让本工具能复用**带扩展的 profile**
（`Chrome.launch` 支持 `userDataDir`，但 `CdpWebDriverOptions` 没接出来）。本轮**刻意不做**：
先让公告说实话，而不是先加能力。

### 记-19. 审计落盘：与 `devdata` / `devenv` 共用一份实现（2026-10-03）

**由来**：本包的审计此前只进宿主日志（不持久：日志会被轮转、也未必落盘），而 `devdata` 早就有
JSONL 出口。三包各写一份必然漂，于是按「第三个消费者出现就上收」把它搬进
`@hyzyn/dsh-kit/audit`（`kit` 0.7.0 的子路径导出——它 `import 'node:fs'`，不能进会被客户端半体
打包的主入口）。

| 落点 | 内容 | 门槛（已验） |
|---|---|---|
| `plugin.ts` 的 `webAuditSink()` | 抽出成导出函数：配了 `auditFile` 走 JSONL（**持久，写失败 = 抛**），没配走 logger（允许 → `info` / 拒绝 → `warn`） | `plugin.test.ts` 3 条：解析（去空白 / 不写 = 只进日志）、落盘两行（允许 + 被拒带码）、日志路由与话术 |

不返回结果**（fail-closed）。
